# 0.5.4 升级与 IP 隔离恢复

配套版本：后端 **0.5.4**、前端 **0.5.3**、Agent **0.5.4**。三个组件都要更新；旧固定版本和安装包不会覆盖。

这次修复的是：宿主安装了另一个同名 `arping` 包后，空闲地址的探测超时被旧 Agent 当成占用，控制面逐个隔离候选 IP，最终地址池耗尽。更换系统软件包不会自动清除数据库里的旧隔离记录。

## 1. 已经部署的人，先看这里

只更新前后端镜像不够，本次必须逐宿主更新 Agent。

1. 维护窗口内暂停新申请和管理员操作，确认没有在途任务；备份原数据库、部署配置及每台 Agent 的配置和状态目录。
2. 后端镜像改为 `lixiaokun/vmp-backend:0.5.4`，前端镜像改为 `lixiaokun/vmp-frontend:0.5.3`。使用原 Compose 项目及原覆盖文件，只更新这两个服务，不重建数据库。
3. 后端启动会自动执行 **021** 迁移。内置和外置 PostgreSQL 都一样，不需要挂 SQL、不需要手工运行初始化脚本。原数据库账号须有执行迁移所需的 DDL 权限。
4. 每台可执行任务的 KVM 宿主更新为 Agent **0.5.4**，保留原部署账号、host ID、独立凭据、`AGENT_STATE_DIR`、配置、实例目录和镜像缓存。
5. 确认 Agent 实际调用的是 `iputils-arping`；完成预检后启动，再检查宿主心跳及网桥就绪。
6. 前端刷新后进入“网络 IP”，先复核隔离地址；或在原失败实例上点击“重试创建”，让平台自动复核隔离候选。
7. 通过验收后恢复调度及业务入口。

本次没有要求新增必填环境变量。原来的 `KVM_ARPING_PATH` 仍有效，默认 `/usr/bin/arping`；不要重新生成数据库密码、加密密钥或控制台签名密钥，也不要重新签发仍正常的宿主身份。

旧 0.4.x 共享令牌环境仍须先按 [主手册第 22 节](新手部署手册.md#22-升级) 完成独立身份迁移，不能只替换二进制。

### 控制节点：更新镜像

在自己的原 `.env` 或部署清单中修改：

```dotenv
VMP_BACKEND_IMAGE=lixiaokun/vmp-backend:0.5.4
VMP_FRONTEND_IMAGE=lixiaokun/vmp-frontend:0.5.3
```

下面是内置数据库 Compose 的示例。若你使用外置数据库、自定义文件或项目名，必须使用原来的 `-f` / `-p` 参数，不能照抄成另一个部署项目。

```bash
docker compose --env-file .env -f compose.yaml pull control-plane web
docker compose --env-file .env -f compose.yaml up -d --no-deps control-plane
docker compose --env-file .env -f compose.yaml ps
docker compose --env-file .env -f compose.yaml logs --tail=80 control-plane
# 后端健康并完成迁移后，再更新前端。
docker compose --env-file .env -f compose.yaml up -d --no-deps web
```

不要运行 `docker compose down -v`。若挂载静态前端目录，须一起替换完整 HTML / JS / CSS，不能让旧挂载覆盖新镜像。

### KVM 宿主：确认 ARP 软件包

以原 Agent 运行账号查看实际配置的工具。以下使用默认路径：

```bash
dpkg-query -W arping iputils-arping 2>/dev/null
/usr/bin/arping -V
```

正确的版本输出应能识别 `iputils`。另一个 `arping` 包的 `-D` 是显示模式，不是重复地址检测，其无响应退出码与 iputils DAD 含义相反。不要仅判断“系统有 arping 命令”。

Ubuntu / Debian 安装前先查看包变更计划：

```bash
sudo apt-get -s install iputils-arping
```

确认只发生预期软件包替换、没有删除虚拟化或网络依赖后，再安装：

```bash
sudo apt-get install iputils-arping
```

该操作不修改宿主机网桥/IP，但软件包管理器可能替换另一个 `arping` 包；不要额外重启宿主网络或 libvirt。非 root Agent 仍需执行 ARP 所需权限，不能用开放目录权限绕过。

### KVM 宿主：下载并替换 Agent

下载位置：[Agent 0.5.4](https://github.com/lixiaokun777/vmp-agent/releases/tag/v0.5.4)。选择宿主架构的 `vmlease-agent-linux-amd64.tar.gz` 或 `vmlease-agent-linux-arm64.tar.gz`，并用同一 Release 的 `SHA256SUMS` 校验。

维护期间将包解压到新的 staging 目录，不直接覆盖运行目录。以原部署账号停止 Agent，确认进程退出且没有在途任务，备份原二进制后替换 `vmlease-agent`。不要用示例配置覆盖现有 `agent.env`，不要删除 `run/state` 或 `credentials.json`。按原部署目录和配置运行：

```bash
./control.sh preflight
./control.sh start
./control.sh status
```

如果使用 `VMLEASE_AGENT_CONFIG` 或自定义状态目录，预检和启动必须使用与原进程相同的配置。完整停止、备份、替换和回滚步骤见 [主手册第 22.5 节](新手部署手册.md)。

## 2. 网页恢复被误隔离的地址

只有管理员可操作。普通用户不能修改地址池或解除隔离。

进入“网络 IP”，选择对应网络，筛选“隔离”：

- **重新探测**：在就绪宿主的真实网桥上检查一次，记录结果，仍保持隔离；适合先排查。
- **探测并解除隔离**：提交新探测任务，只有本次确认无冲突，且地址仍为隔离、没有实例绑定时，才恢复空闲。
- **批量复核隔离 IP**：按有限批次处理当前网络的隔离地址；有剩余时继续提交下一批。不会处理已分配、已预留或保留期实例的 IP。

这是异步任务。提交成功不等于地址已空闲；页面会显示“探测中”和最新结果。若工具不兼容、权限不足、宿主离线、探测超时或网桥未就绪，地址不解除隔离，并显示错误原因。真实回应则继续隔离。排队超过 10 分钟仍未执行的复核会由后台关闭并记为错误，可以核查宿主后再次提交；已经领取的任务仍受租约保护，不接受旧领取结果。

本版没有“不经探测强制置为空闲”入口。`.131` / `.132` 等已有回应的地址须先查清设备归属，不要整池清空。ping 不通不证明空闲：关机、ICMP 防火墙或临时断网都可能无回应。

升级不会自动改写所有历史隔离记录；这是为了避免把真实外部设备地址一起释放。编辑相同网络范围，也不等于解除隔离。

## 3. 原失败实例怎样重试

在原失败实例点击“重试创建”，不要反复新建申请。

1. 有 `FREE` 地址时，原子预留并重新排队；Agent 创建前仍会探测。
2. 没有 `FREE`、但有未绑定的隔离候选时，进入“正在复核隔离 IP”流程，逐个检查候选，发现安全地址后恢复预留并继续原创建任务。
3. 真实占用继续隔离并检查下一个；探测异常停止恢复，不污染其他候选，也不盲目创建。
4. 无候选、候选均占用或宿主不就绪时，显示相应原因。再次重试重新发起有限复核，不无期限后台循环。

复核期间的 `ERROR` 表示原创建尚未完成，不代表探测已经失败；看详情中的恢复状态和关联任务。重复点击不重复申请资源，不重复增加配额预留；实例已删除、原域状态不确定或存在托管域但 IP 关系丢失时，仍拒绝盲目重建。

创建重试不会自动重新计算租期，需核对原到期时间。若原租期已结束，请按平台允许的正常流程处理，不用数据库改日期绕过校验。

## 4. 保留期 IP 与外部 DHCP

你的担心成立。保留期虚机关机后，IP 往往不再响应 ping / ARP，但平台仍保持该 IP 与实例的绑定；在最终删除成功前，不会再分配给平台内其他实例。

**平台数据库中的保留并不能让外部 DHCP 知道这个 IP 已被保留。** 当前没有自动操作外部 DHCP 服务、代答 ARP 或持续占住地址的功能。

例如平台范围是 `10.200.9.130–10.200.9.150`：

1. 在 DHCP 服务器将这整个范围排除出动态分配池，包含平台空闲、运行中、停止中和保留中的地址。
2. 若这些地址已有外部 DHCP 租约，先核查租约及设备，再调整地址规划；仅改 DHCP 范围不会立即让已有设备放弃地址。
3. 不建议用无归属的 DHCP 保留条目“假占住”地址；使用你的 DHCP 产品支持的正式排除范围，或按可控静态 MAC/IP 规划。
4. 新 Agent 在已停止托管域开机 / 保留期恢复前重新检查原 IP。发现冲突或无法可靠探测时拒绝启动，不换 IP、不删磁盘、不释放绑定。先处理外部冲突，再重试恢复。
5. 恢复启动失败会保留原保留期和恢复次数，不把一次失败当作已成功使用恢复机会；实际超过保留期仍按原规则处理，不无限延长。

ARP 能降低同一二层网络当前冲突的风险，但探测后设备仍可能改变地址，不能提供全网永久防冲突保证。网络规划仍必须先做好。参考：[DHCP 分配机制 RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html)、[IPv4 冲突检测 RFC 5227](https://www.rfc-editor.org/rfc/rfc5227.html)。

## 5. 验收与回滚

升级后至少核对：

- 后端健康且迁移 021 完成，原用户 / 实例 / 配额 / 密钥没有被重建。
- 全部任务执行宿主使用 Agent 0.5.4 与 iputils-arping，网桥就绪。
- 管理员可以复核单地址及批次；普通用户接口返回 403。
- 探测失败不产生新隔离，也不解除原隔离；真实占用继续隔离。
- 原失败实例可自动复核隔离地址；找出空闲地址后继续原任务，不重复扣预算。
- 保留期 IP 仍绑定原实例；外部冲突时不启动、不删盘、不释放 IP。
- DHCP 排除范围已由网络管理员核实。

本版的实际自动化验证范围见 [0.5.4 发布验收](0.5.4发布验收.md)。隔离数据库、Linux 探测和浏览器验收不等于已在你的生产宿主写操作验收。本轮发布不自动升级 144 / 172 / 170 / 174，不自动恢复任何生产隔离地址。

回滚前先暂停业务并清空在途新探测任务。保留 021 表结构通常可兼容旧应用，但旧 Agent 存在本次误判风险，不能恢复旧包后继续复核地址；完整数据库回滚应结合维护前备份并评估期间业务变更，不直接删除迁移列或台账。
