# 0.8.0 发布与升级

配套版本：后端 **0.8.0**、前端 **0.8.0**、Agent **0.7.3**。三个组件版本号不必相同，不要误找 Agent 0.8.0 包。固定发布由 GitHub Actions 验证后生成，旧标签不覆盖；发布不自动升级任何服务器。

## 这版包含什么

- 管理员“平台策略 → 虚拟机调度”：剩余资源优先、轮询分配、资源均衡；有只读预览、跳过原因及实例/审计调度记录。升级默认保持剩余资源优先，不迁移旧实例。
- 前端修复未保存密码/宿主凭据确认弹窗错位，桌面及窄屏布局均已隔离验收。
- Agent 0.7.3 修复目标域和磁盘已经删除后，旧镜像缓存核验异常仍导致 DELETE_INSTANCE 失败。实际删除/落盘失败仍阻断，未知引用缓存继续保护并记录告警，不放宽共享 backing 回收。
- 后端和 Agent 由 Go 1.27.3 构建，修复标准库 GO-2026-6809；回归、静态检查和漏洞门禁继续保留。

## 是否新增配置

**没有新增必填环境变量，没有 Agent 配置改动，也不需要重新签发已有独立宿主凭据。** 后端启动自动执行 `024_scheduling_policy.sql`，不要手工导 SQL，也不要重建数据库。新调度规则在页面选择后保存，不在 agent.env 中配置。

0.5.x / 0.7.x 已有独立宿主身份的环境可按下面更新。仍使用 0.4.x 全局共享运行令牌的环境，应先按 [身份与凭据加固](身份与凭据加固.md) 完成每宿主身份迁移，不能直接照搬旧共享令牌启动新 Agent。

## 第一步：备份，保留原配置

在维护窗口暂停新增申请/审批，记录当前镜像版本；备份 PostgreSQL、原 Compose 或 Kubernetes 配置、密钥、Agent 配置及完整状态目录。不要把密码、令牌和备份提交到开源仓库。不要执行 `docker compose down -v`，不要清理 `.vmp-cache`、虚机数据目录或 Agent 状态。

以下 Compose 命令在原后端项目目录运行，假定 `.env` 位于当前目录。若用外部数据库，把每条命令的 `compose.yaml` 替换为 `compose.external-db.yaml`；若原部署使用其他路径/项目名，应继续沿用，不能另起一套空平台。

## 第二步：更新后端和前端

只修改你**现有** `.env` / 部署定义中的两项，不要用示例文件覆盖自己的配置：

```dotenv
VMP_BACKEND_IMAGE=lixiaokun/vmp-backend:0.8.0
VMP_FRONTEND_IMAGE=lixiaokun/vmp-frontend:0.8.0
```

```bash
# 拉取两份新镜像，但先只启动后端。
docker compose --env-file .env -f deployments/compose/compose.yaml pull control-plane web
docker compose --env-file .env -f deployments/compose/compose.yaml up -d control-plane
docker compose --env-file .env -f deployments/compose/compose.yaml logs --tail=100 control-plane
docker compose --env-file .env -f deployments/compose/compose.yaml ps

# 等后端健康、024 迁移成功后，再更新网页。
docker compose --env-file .env -f deployments/compose/compose.yaml up -d web
```

如果 `.env` 中写了旧固定标签，新下载的 Compose 默认值不会替你覆盖它。手工 Kubernetes/Helm 部署则更新原工作负载的后端/前端镜像，同样先等待后端启动健康与迁移完成，再滚动前端，不另建数据库或命名空间。

确认管理员页面可打开调度卡片；刷新后设置保留。选择轮询或均衡必须点击“保存平台策略”。预览只读，不检查某个申请人的额度或是否有空闲 IP，最终以实际提交时检查为准。规则详见 [调度策略](调度策略.md)。

## 第三步：逐台更新 Agent 0.7.3

1. 暂停该宿主新增调度，确认没有在途任务；暂停调度本身不会取消已经产生的到期、删除等任务。
2. 在宿主机上按架构从 [Agent v0.7.3](https://github.com/lixiaokun777/vmp-agent/releases/tag/v0.7.3) 下载安装包和 `SHA256SUMS`。amd64 对应 x86_64，arm64 对应 aarch64，核对完整摘要后再解包到新的临时目录。
3. 用原运行账号在原安装目录执行 `./control.sh stop`；确认旧进程退出后，备份原二进制、配置和完整 `AGENT_STATE_DIR`，保持私有权限。不能只备份或删除 credentials.json。
4. 替换原目录的 `vmlease-agent` 二进制，按需更新脚本和文档；**保留**原 `conf/agent.env`、身份/任务/回执状态、存储/镜像/缓存目录。不要把包中的 `.example` 覆盖成现网配置。
5. 原账号执行 `./control.sh preflight`、`./control.sh start`、`./control.sh status`。网页确认宿主在线、资源/镜像/网桥报告新鲜，再恢复调度。保持原启动方式，不添加 systemd 要求。

精确升级/回滚及权限说明见包内 `docs/部署与运维.md`。单纯选择调度策略不需要改 Agent，但删除任务修复必须替换这个二进制，仅换前后端镜像不会修好。

## 旧删除任务怎么恢复

- 仍是 PENDING / 等待重试：新 Agent 恢复领取后会继续原任务，成功后控制面释放 IP/配额并清理实例记录；不要再并行提交其他删除操作。
- 已经 FAILED：升级不会自动修改历史任务。管理员在实例页面确认目标后使用“立即删除”重新提交 DELETE_INSTANCE，**不是“重试创建”**。最终失败通常退回保留状态；新 Agent 对目标已不存在的删除可幂等确认成功。
- 日志出现 `cache_unpin_deferred`：目标资源已确认删除，但旧缓存仍保护。按日志中的异常实例 ID 核对清单/索引，不手工删共享基础盘。该告警不表示实例磁盘仍存在，也不阻止已完成删除的确认。

## 升级验收和回滚

检查普通用户隔离、管理员策略保存与只读预览；在明确授权的测试实例上验收创建、删除和 IP/配额释放，不拿业务 VM 试强删。已有 VM 不会自动迁移，也不会自动重启或改 CPU 模式。

本地回归使用专用 PostgreSQL 16、Go 1.27.3、模拟 Agent / 临时磁盘目录以及前端 69 项测试；浏览器检查 320–1440px 和保存/重复预览。发布工作流再做测试、漏洞检查、双架构构建及远端清单验证。隔离回归不等于内网业务宿主已经升级验收。

如需回滚，先恢复“剩余资源优先”，暂停新增写入并确认在途任务状态，再恢复原镜像和匹配的 Agent 二进制。024 为增量字段/表，旧后端不认识新策略，因此不会遵守轮询/均衡。不要直接删迁移台账或手工撤销表结构；数据库恢复须使用一致性备份和维护窗口，不以丢失新实例记录换取表面回滚。
