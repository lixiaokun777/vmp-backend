# VMP 从零部署和日常运维手册

适用版本：后端 **0.5.3**、前端 **0.5.2**、Agent **0.5.3**。更新日期：2026 年 10 月 10 日。

三个版本号不同是正常的：后端 0.5.3 增加安全凭据元数据，前端 0.5.2 提供网页签发和紧凑布局，Agent 继续使用 0.5.3。沿用 0.5.1 的独立身份、任务和就绪协议，本轮没有新增迁移或配置项。不要为了让版本号一致而换回旧 Agent，也不要在生产环境长期使用 latest。

本文从空控制节点开始，说明数据库、Web、KVM Agent、网络、镜像和管理员配置，直到真正申请出一台能登录的虚拟机。已经部署好的平台请直接看第 22 节，不要重新初始化数据库或重新注册宿主。

**本手册中的地址、密码、目录示例需要按自己的环境修改。文档没有放任何真实密码、令牌或机器人 key。**

当前界面边界也写明在操作处：前端 0.5.2 提供宿主页签发 / 轮换按钮和管理 IP 展示，日常按第 22.6.1 节页面操作；旧前端 0.5.1 没有该入口。分层交付状态仍需通过详情 API 核对；异常状态的救援控制台需要手工打开同源控制台页；本地镜像没有独立摘要输入框。不要把后端支持的接口等同于旧镜像已有按钮。

## 1. 平台组成和执行位置

### 1.1 先分清三种机器

| 名称 | 安装什么 | 不安装什么 | 作用 |
| --- | --- | --- | --- |
| 控制节点 | Docker、后端容器、前端容器；可选 PostgreSQL 容器 | 不需要 KVM，不存新虚拟机的系统盘 | 用户登录、配置、调度、审批和审计 |
| KVM 宿主机 | 已有 libvirt / QEMU、Agent、镜像及专用实例目录 | 不需要为了运行 Agent 安装 Docker 或 Go | 真正创建、开关机和删除虚拟机 |
| 新申请的虚拟机 | 镜像中的系统、SSH、cloud-init；按模板预装 Docker 等 | 不安装宿主 Agent | 给研发人员使用 |

Agent 使用 Go 二进制和 control.sh 启停，不使用 systemd 管理 Agent。Docker 和 libvirt 自身仍按操作系统的服务机制运行，这与“不用 systemd 启动 Agent”不矛盾。

控制面不需要保存宿主机 SSH 密码，也不会通过 SSH 登录宿主执行任务。

### 1.2 数据流和文件位置

~~~text
浏览器
  │  HTTP / HTTPS，同一个平台地址
  ▼
控制节点 Web / Nginx
  │  /api/，包括控制台 WebSocket
  ▼
控制面 / Go ─── PostgreSQL：用户、实例、审批、配置、任务和审计
  ▲
  │  Agent 主动注册、心跳、领取任务、回传结果
  │
KVM 宿主机 Agent ─── 本机 libvirt / QEMU
  ├── 镜像目录：原始 cloud image
  ├── 缓存目录：受保护的基础 backing 文件
  └── 实例目录：每台新虚拟机的系统盘、seed 和清单

控制台单独链路：
浏览器 → 平台同源 WebSocket → 控制面 → 宿主 Agent:19090 → 本机 VNC / 串口
~~~

**数据库不等于虚拟机磁盘。** 只备份 PostgreSQL，不能恢复已删除的 qcow2 系统盘；只备份系统盘，也不能恢复平台用户、IP 分配和审批状态。

### 1.3 本手册采用的示例

| 项目 | 本文示例 | 你需要替换为 |
| --- | --- | --- |
| 控制节点 | 10.0.0.10 | 用户和 Agent 都能访问的平台节点 |
| KVM 宿主机 1 | 10.0.0.21 | 控制节点能访问的宿主 IP |
| 宿主唯一名称 | kvm-node01 | 每台不同，不要重复 |
| 用户访问地址 | http://10.0.0.10:8080 | 正式环境推荐 HTTPS 域名 |
| 网络 | 10.0.0.0/24 | 宿主网桥真实接入的网络 |
| 网关 | 10.0.0.1 | 该网络的真实网关 |
| 分配范围 | 10.0.0.130–10.0.0.150 | 经网络管理员确认的专用范围 |
| DNS | 10.0.0.2 | 虚拟机能访问的 DNS |
| 网桥 | br0 | 宿主机实际存在、已启用的 Linux bridge |

示例范围包含 21 个地址，不是整个 /24 都归平台使用。CIDR 是网络掩码，起止 IP 是平台可以分配的地址池，两者不是一回事。

### 1.4 终端到底在哪台机器打开

你的 Mac / Windows 电脑只用于 SSH 登录和浏览器访问。下面的 apt、Docker、Agent 命令都在指定的 Linux 服务器上执行，不在 Mac 本机执行。

建议同时打开两个终端窗口，分别用于控制节点和宿主：

~~~bash
# 在自己电脑终端执行。ubuntu 是示例控制节点系统账号，按实际替换。
ssh ubuntu@10.0.0.10
~~~

~~~bash
# 在自己电脑的另一个终端执行。ops 是示例宿主运维账号，按实际替换。
ssh ops@10.0.0.21
~~~

第一次连接先按组织资产信息核验 SSH 主机指纹；不要忽略“主机密钥已变化”告警。输入系统登录密码时屏幕通常不显示字符，这是正常的。没有 SSH 权限时请由已有授权的运维人员执行，不需要把宿主密码填到 VMP 页面。

每次准备执行一节前，在该终端先确认机器：

~~~bash
hostname
hostname -I
whoami
pwd
uname -m
~~~

看 hostname / IP 是否与该节“执行位置”匹配。sudo 要求的是服务器系统账号权限 / 密码，不是平台管理员 admin 的密码。后面 sudo -u vmpagent 表示让已登录的运维人员以 Agent 专用账号运行本条命令，不代表你需要给 vmpagent 开放 SSH 登录。

遇到报错立即停在当前步骤，先对照“预期结果”和第 25 节排障。不要一次性粘贴整篇文档，不要失败后继续执行下一节，不要将 A / B 两条互斥路线都执行。含“替换为……”的占位值必须先改成真实配置。

## 2. 准备自己的部署信息

部署前填写一份自己的信息表，后面不要边做边猜。

### 2.1 控制节点

建议 Ubuntu 22.04 / 24.04，64 位，4 核 CPU、8 GiB 内存、50 GiB 可用磁盘。2 核 / 4 GiB 可以用于小规模验证；这些是部署建议，不是平台强制门槛。

控制节点需要：

- 可以访问 Docker Hub 和 GitHub，或者已有可信的内网镜像和安装包；
- 可以访问数据库；
- 宿主机能访问它的 Web 地址；
- 用户能访问 Web；
- 启用控制台后，控制面容器可以访问宿主代理端口；
- 开启 LDAP / 通知时，容器可以访问目录服务和机器人 HTTPS 地址；
- 系统时间正确，建议使用组织的 NTP。

### 2.2 每台宿主机

登记以下信息：

| 信息 | 为什么要登记 |
| --- | --- |
| CPU 架构：x86_64 或 aarch64 | 决定下载 amd64 还是 arm64 Agent 和镜像 |
| 管理 IP、唯一名称 | 纳管身份和控制台拨号 |
| libvirt URI 和已有域清单 | 防止连错 libvirt 实例或误判存量虚机 |
| 网桥名和 VLAN / 二层网络 | 静态 IP 必须落到正确网络 |
| 现有业务内存占用和可留出的预算 | 平台不能占用宿主全部物理内存 |
| 专用实例、镜像、缓存目录 | 不与已有业务磁盘混用 |
| QEMU 实际运行用户 / 组 | 基础缓存和新系统盘需要能被 QEMU 读取 |
| Agent 启动账号 | 后续重启和升级必须沿用，不能随意换成 root |

宿主已经有重要虚拟机时，不要为安装 Agent 重装 KVM、重建网桥、全盘升级或重启 libvirt。

### 2.3 端口和访问方向

| 从哪里访问 | 到哪里 | 端口 | 是否需要公网开放 |
| --- | --- | --- | --- |
| 用户浏览器、宿主 Agent | 控制节点 Web | 8080；正式入口通常 443 | 按组织要求开放平台入口 |
| 控制面容器 | PostgreSQL | 5432 或实际端口 | 不需要开放给用户 |
| 控制面容器 | 宿主 Agent 控制台 | 默认 19090，可选 | 不需要，只允许控制节点实际来源 IP |
| 研发用户 | 申请出的虚拟机 | SSH 22 和业务端口 | 按研发网络权限开放 |
| 控制面容器 | LDAP | 636 / 389 或实际端口 | 不需要 |
| 控制面容器 | 群机器人 | 443 或实际 HTTPS 端口 | 只需出站连接 |

内置数据库和后端都没有映射宿主 5432 / 8080 端口；映射出来的 8080 是 Web。不要额外把后端、libvirt TCP 或各台 VNC 端口暴露到公网。

Docker 的端口映射有自己的防火墙处理，不要仅凭 UFW 状态认定端口已受限。相关限制见 [Docker 官方安装说明](https://docs.docker.com/engine/install/ubuntu/)。

## 3. 配置文件、令牌和密钥

### 3.1 两个配置文件分别在哪

| 文件 | 所在机器 | 谁读取 | 修改后怎样生效 |
| --- | --- | --- | --- |
| 后端仓库根目录 .env | 控制节点 | Docker Compose | 重建对应容器；仅 restart 不会换环境变量 |
| Agent 的 conf/agent.env | 每台 KVM 宿主机 | control.sh，再传给 Agent | 使用原启动账号执行 restart |
| LDAP / 通知 / 平台策略 | PostgreSQL，由管理员页面维护 | 后端 | 页面保存后生效，不需要修改每台 Agent |

控制节点 .env 是 Compose 的配置；Agent 的 agent.env 是 shell 加载的配置。不要把两份文件互相覆盖，也不要在控制节点执行 source .env：LDAP 过滤器等 dotenv 内容不一定是合法 shell，且 source 会执行文件内容。

### 3.2 哪些值不能随便填

| 配置 | 用途 | 推荐填写 | 必须备份吗 |
| --- | --- | --- | --- |
| POSTGRES_PASSWORD | 内置数据库密码 | 独立随机十六进制字符串 | 必须 |
| BOOTSTRAP_ADMIN_PASSWORD | 空库首次创建管理员 | 至少 10 位，含大写、小写和数字 | 首登改密后从部署环境清空 |
| AGENT_BOOTSTRAP_TOKEN | 新宿主首次纳管 | 独立生成 32 字节随机值，即 64 位十六进制 | 必须，且不能公开 |
| SETTINGS_ENCRYPTION_KEY | 加密 LDAP 密码、机器人 key 等配置 | 另一个独立 64 位十六进制值 | 必须，丢失后无法解密旧配置 |
| CONSOLE_SIGNING_KEY | 控制台票据签名和校验 | 另一个独立 64 位十六进制值 | 必须，与每台 Agent 完全一致 |
| Agent credentials.json | 单台宿主的长期运行身份 | 首次注册自动生成，不手填 | 必须，不能复制给其他宿主 |

不是把“change-xxx”换成一个容易记的单词就够了。公开示例引导令牌、重复字符等弱值会被后端拒绝；其他密钥也应使用随机值。

分别运行以下命令四次，每次输出用于一个不同字段：

~~~bash
openssl rand -hex 32
~~~

一次输出为 64 个十六进制字符。不要把四个字段都填同一个输出，不要把输出发到群里或提交到 Git。

**AGENT_RUNTIME_TOKEN 的变化：** 当前后端不再使用所有宿主共享的运行令牌。后端 .env 中该项保持空。新 Agent 的 AGENT_HOST_ID / AGENT_RUNTIME_TOKEN 也留空，由首次注册自动取得身份。只有旧版迁移或管理员轮换某台宿主凭据时，才使用这两个 Agent 导入字段。

### 3.3 SESSION_TTL_HOURS=12 是什么

12 表示从本次登录起固定有效 **12 小时**，不是虚拟机租期，也不是闲置 12 小时或每天 12 点退出。请求活动不会滑动延长会话；超过有效期需要重新登录，关闭浏览器不等于自动续期。

不熟悉时保持 12。修改为 8 就是 8 小时。不能用它控制虚拟机能用几天，虚拟机时长在申请表填写。

### 3.4 密码特殊字符有两层规则

第一层是配置文件的引号：

- Compose .env 中，含 $ 等特殊字符的密码建议用单引号包住，防止变量插值；
- Agent agent.env 是 shell 文件，字符串也建议用单引号，等号两侧不要加空格；
- 新手最容易处理的是随机十六进制令牌 / 数据库密码，不含这些特殊字符。

Compose 单引号按字面值处理，规则见 [Docker Compose 环境变量说明](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

第二层是数据库连接 URL：

~~~text
postgres://用户名:密码@数据库地址:5432/数据库名?sslmode=...
~~~

这里密码中的 @ 是 URL 分隔符，必须编码。**加引号只能保护配置读取，不能代替 URL 编码。**

| 原字符 | URL 编码 |
| --- | --- |
| @ | %40 |
| : | %3A |
| / | %2F |
| ? | %3F |
| # | %23 |
| % | %25 |
| 空格 | %20 |
| + | %2B |
| $ | %24 |

假设密码是示例值 Demo@2026!，可以写：

~~~dotenv
DATABASE_URL='postgres://vmp_app:Demo%402026%21@db.example.internal:5432/vmlease?sslmode=require'
~~~

数据库真正的密码仍是 Demo@2026!，不是 Demo%402026%21。只对用户名 / 密码等 URL 组成部分编码，不要把整个连接 URL 编码。URL 规则见 [PostgreSQL 连接说明](https://www.postgresql.org/docs/16/libpq-connect.html)。

内置数据库 Compose 会直接拼接 POSTGRES_PASSWORD。因此方案 A 用不含特殊字符的十六进制密码；需要保留已有复杂密码时用方案 B 的完整 DATABASE_URL，不要把编码后的密码拿去初始化 PostgreSQL。

### 3.5 文件保护

配置文件权限应为 0600，目录尽可能仅管理员 / Agent 账号可访问。不要上传 .env、agent.env、credentials.json、数据库备份、Webhook 完整地址或包含票据的日志。

docker compose config 的默认输出会包含展开后的密码和密钥。本文用 config --quiet 校验，不打印整份配置；需要排查时也不要把敏感输出直接贴到工单或群聊。

## 4. 控制节点安装 Docker

**执行位置：控制节点。已经能正常运行 Docker 和 Compose 的机器跳过安装，仅执行检查。不要在 KVM 宿主机照抄此节。**

### 4.1 先检查

~~~bash
uname -m
lsb_release -ds
sudo docker version
sudo docker compose version
~~~

最后两条成功就不用重装。Compose 必须是带空格的 docker compose 插件；不要混用旧 docker-compose 命令。

### 4.2 新的 Ubuntu 控制节点安装

下面只适用于空的 Ubuntu 22.04 / 24.04 控制节点。已有 Docker、containerd 或其他容器业务时，先按组织规范确认兼容性，不要直接卸载现有包。

~~~bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git openssl nano
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
lsb_release -cs
dpkg --print-architecture
sudoedit /etc/apt/sources.list.d/docker.sources
~~~

编辑器中填写下面内容。Ubuntu 24.04 的 Suites 是 noble，22.04 是 jammy；Architectures 使用上一步输出 amd64 或 arm64，不要照抄错架构：

~~~text
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
~~~

保存后：

~~~bash
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker version
sudo docker compose version
~~~

安装方式依据 [Docker 官方 Ubuntu 安装文档](https://docs.docker.com/engine/install/ubuntu/)。不要在生产环境执行来历不明的一键安装脚本。

后续 Docker 命令统一使用 sudo，避免“加入 docker 组后没有重新登录”的困惑。docker 组本身具有高权限，不要给所有普通平台用户加入该组。

## 5. 下载部署文件和选择数据库方案

**执行位置：控制节点。**

~~~bash
sudo install -d -m 0750 -o "$(id -un)" -g "$(id -gn)" /opt/vmlease-src
cd /opt/vmlease-src
git clone --branch v0.5.3 --depth 1 https://github.com/lixiaokun777/vmp-backend.git
cd /opt/vmlease-src/vmp-backend
cp .env.example .env
chmod 600 .env
~~~

Compose 项目名固定为 vmlease。不要随意改成另一个 -p 项目名，否则可能创建另一份空数据库卷，看起来像数据丢失。已有环境始终沿用原项目名和卷。

这里固定代码标签 v0.5.3，Compose 使用后端 0.5.3 和前端 0.5.2 镜像。使用镜像部署不需要克隆前端、安装 Node.js 或编译 Go。

如果该目录已有项目，不要再 clone 或覆盖 .env，转第 22 节。

### 5.1 只能选择一种数据库方案

| 方案 | 启动文件 | 会启动哪些服务 | 适用情况 |
| --- | --- | --- | --- |
| A：自带数据库 | deployments/compose/compose.yaml | postgres、control-plane、web | 没有 PostgreSQL，希望先开箱使用 |
| B：已有数据库 | deployments/compose/compose.external-db.yaml | control-plane、web | 组织已有 PostgreSQL 或云数据库 |

不要把 external-db.yaml 叠加到完整 compose.yaml 上；否则 postgres 服务仍存在。不要在同一台机器、同一个项目名和端口同时启动 A、B 两套。

### 5.2 后续命令简写

下面用一个 shell 函数 vmpc，减少每次输入很长的参数。它不是额外安装的软件，只对当前终端有效。新开终端时要重新定义相同方案的函数。

方案 A：

~~~bash
vmpc() {
  sudo docker compose --env-file /opt/vmlease-src/vmp-backend/.env \
    -f /opt/vmlease-src/vmp-backend/deployments/compose/compose.yaml "$@"
}
~~~

方案 B：

~~~bash
vmpc() {
  sudo docker compose --env-file /opt/vmlease-src/vmp-backend/.env \
    -f /opt/vmlease-src/vmp-backend/deployments/compose/compose.external-db.yaml "$@"
}
~~~

例如，vmpc ps 相当于带完整路径执行 docker compose ps。本文后续 vmpc 命令都要求你已经按实际方案定义函数。已有部署路径或自定义 Compose 必须使用自己的文件，不要改用本手册的默认路径。

## 6. 两种数据库部署步骤

### 6A. 自带 PostgreSQL

**执行位置：控制节点。只执行 A 或 B，不要都执行。**

#### 第一步：编辑 .env

~~~bash
cd /opt/vmlease-src/vmp-backend
nano .env
~~~

至少修改下面这些项。“替换为……”是说明，不是可用配置值：

~~~dotenv
# 内置数据库：三个名称在首次启动后不要随意改变。
POSTGRES_DB=vmlease
POSTGRES_USER=vmlease
POSTGRES_PASSWORD=替换为单独生成的64位十六进制随机值

# 用户访问平台的监听地址和端口。
VMP_HTTP_BIND=0.0.0.0
VMP_HTTP_PORT=8080

# 固定组件版本。
VMP_BACKEND_IMAGE=lixiaokun/vmp-backend:0.5.3
VMP_FRONTEND_IMAGE=lixiaokun/vmp-frontend:0.5.2

# 新宿主注册用；不能沿用公开示例值。

AGENT_RUNTIME_TOKEN=

BOOTSTRAP_ADMIN_PASSWORD='替换为至少10位含大小写字母和数字的强密码'

# 登录12小时后重新认证；HTTP验证阶段为false。
SESSION_TTL_HOURS=12
SESSION_COOKIE_SECURE=false
TRUSTED_PROXY_CIDRS=

# 再各自生成一个不同随机值。

CONSOLE_SIGNING_KEY=替换为另一个64位十六进制随机值

# 前期不配置LDAP，保留示例文件中的LDAP字段为空或默认值。
LDAP_URL=
LDAP_BASE_DN=
LDAP_BIND_DN=
LDAP_BIND_PASSWORD=
~~~

保留原示例里的其他 LDAP 属性 / 过滤器默认项即可。不要因为复制片段而误删所有其他配置。

nano 中 Ctrl+O 保存，回车确认，Ctrl+X 退出。再次执行 chmod 600 .env。

#### 第二步：校验并启动

先按 5.2 定义方案 A 的 vmpc，再执行：

~~~bash
vmpc config --quiet
vmpc pull
vmpc up -d
vmpc ps
~~~

第一条没有输出且退出成功，说明 Compose 配置可以解析；这不等于密码一定正确、数据库可达或应用已健康。

#### 第三步：数据库初始化说明

PostgreSQL 首次启动建立数据库和用户；后端连接后自动执行编译进镜像的迁移。**不需要挂载 migrations 到数据库，也不需要手工执行初始化 SQL。**

内置数据保存在名为 vmlease_postgres-data 的具名卷中，但实际卷名应通过 docker volume ls 核对。容器可以重新创建，数据卷必须保留。

已有数据卷时，修改 .env 的 POSTGRES_PASSWORD 不会自动修改数据库里已有账号的密码。要改密码需走数据库密码变更流程，并同步连接配置，不能当作首次初始化再来一次。

### 6B. 使用已有 PostgreSQL

**执行位置：数据库管理员准备数据库；控制节点填写连接配置。**

#### 第一步：准备专属数据库

推荐为 VMP 创建独立数据库，不要指向其他业务的共享库，也不要直接连接系统 postgres / template 数据库。当前发布验证使用 PostgreSQL 16。

需要具备：

- 一个已存在的数据库，例如 vmlease；
- 专属登录账号，例如 vmp_app；
- 该账号有目标 schema 的建表、建索引、修改约束及现有 VMP 表的权限；
- pgcrypto 扩展可用；
- 控制面容器的网络来源被允许；
- 数据库连接数量和容量符合组织要求。

以下供 DBA 在 PostgreSQL 管理会话中按流程执行，仅用于新建专属空库，不是让应用连接一个不存在的库：

~~~sql
CREATE ROLE vmp_app LOGIN;
\password vmp_app
CREATE DATABASE vmlease OWNER vmp_app;
\connect vmlease
CREATE EXTENSION IF NOT EXISTS pgcrypto;
GRANT USAGE, CREATE ON SCHEMA public TO vmp_app;
~~~

其中 \password 和 \connect 是 psql 命令，不是普通 SQL。托管数据库使用控制台 / DBA 的等效操作。不要把真实密码写入共享 SQL 文件。

数据库已由旧 VMP 使用时，保留原账号、所有权、库名和数据，先备份；无需再 CREATE DATABASE。后端会自动识别已执行的迁移并补齐后续结构。

#### 第二步：填写 .env

除方案 A 中的令牌、管理员、会话和密钥外，再设置：

~~~dotenv
DATABASE_URL='postgres://vmp_app:已编码的数据库密码@db.example.internal:5432/vmlease?sslmode=require'
~~~

这里 db.example.internal 必须能在控制面容器内解析和访问：

- 外部数据库不能填 localhost / 127.0.0.1；容器里的 localhost 指容器自身；
- Kubernetes 的短服务名不能假定在集群外 Docker 主机可解析；
- 数据库端口不一定是 5432，以实际为准；
- IPv6 地址在 URL 中需要方括号；
- 使用原连接用户名 / 密码的特殊字符编码，见 3.4。

本方案不使用 .env 中 POSTGRES_DB / POSTGRES_USER / POSTGRES_PASSWORD 初始化数据库，它们只被方案 A 的 postgres 服务引用。

#### 第三步：TLS 选择

| 设置 | 含义和用途 |
| --- | --- |
| sslmode=disable | 不使用 TLS，只用于严格受控的内网或验证环境 |
| sslmode=require | 要求加密，不能将它等同于完整的主机身份校验 |
| sslmode=verify-full | 校验证书链和主机名，正式外置数据库优先采用 |

私有 CA 需要把 CA 文件只读挂载进控制面容器，并在 DATABASE_URL 指定容器内 sslrootcert 路径；仅把 CA 放在宿主目录不会自动生效。使用托管数据库提供的正式连接方式。不要为让连接成功而关闭证书校验。

#### 第四步：启动

先核对 .env 中 DATABASE_URL 确实存在且不是空值，并且没有保留中文占位密码。当前模板不会自动要求它非空；空值会使程序回退到本机开发连接地址，而不是自动发现组织的数据库。

按 5.2 定义方案 B 的 vmpc，然后：

~~~bash
vmpc config --quiet
vmpc pull
vmpc up -d
vmpc ps
~~~

应该只有 control-plane 和 web，不应多出一个本项目 postgres 容器。

**后端只创建目标数据库中的 VMP 表结构，不创建 PostgreSQL 服务、登录账号或数据库本身。** 连接不存在的数据库仍会失败。

## 7. 启动后检查和首次管理员登录

**执行位置：控制节点检查；浏览器登录。**

### 7.1 检查容器和日志

~~~bash
vmpc ps
vmpc logs --tail=150 control-plane
vmpc logs --tail=80 web
curl -fsS http://127.0.0.1:8080/api/v1/health
~~~

如果你改过端口，替换 8080。使用外部 HTTPS 网关时也检查正式域名的同一路径。

预期：

- 后端 healthy，不是不断 Restarting；
- 内置方案的 postgres healthy；
- web 为 Up；
- 健康接口返回 status 为 ok；
- 后端日志出现 database migrations ready 和监听信息。

应用启动先取得数据库锁、执行未应用的迁移、检查已执行文件的 SHA-256，再提供服务。迁移逐个事务执行：失败的当前迁移回滚，已完成的前序迁移仍保留，不是整批同时回滚。当前最高迁移是 020_platform_governance.sql，共 20 条。失败时应用拒绝启动，不应删除 schema_migrations 或改旧 SQL 来绕过。

方案 A 可只读检查：

~~~bash
vmpc exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) AS applied_count, max(version) AS latest FROM schema_migrations;"'
~~~

外部数据库由 DBA 在对应数据库执行相同 SELECT。无需让普通平台用户接触数据库。

### 7.2 首次登录

浏览器打开：

~~~text
http://10.0.0.10:8080
~~~

1. 选择“平台账号”，不是 LDAP；
2. 输入 .env 的 BOOTSTRAP_ADMIN_USERNAME / BOOTSTRAP_ADMIN_PASSWORD；
3. 根据首登提示设置新密码；
4. 确认侧边栏出现管理员的宿主机、网络 IP、用户管理等页面。

首次初始化密码只在空库首次创建该管理员时使用。数据库里同名用户已经存在时，不会覆盖密码，也不会把已有普通账号提升为管理员。

### 7.3 清除环境中的初始管理员密码

确认新密码可以正常登录后，编辑 .env：

~~~dotenv
BOOTSTRAP_ADMIN_PASSWORD=
~~~

再执行：

~~~bash
vmpc up -d --no-deps --force-recreate control-plane
curl -fsS http://127.0.0.1:8080/api/v1/health
~~~

这个命令只重建后端，不重建 PostgreSQL，不清空已存在的管理员。不要仅执行 restart，环境变量变更需要 recreate。

### 7.4 配置后端信任的 Web 代理

默认后端只看到 web 容器地址；不配置信任时，多名用户可能共享来源 IP 的登录限流。

~~~bash
vmp_web_id=$(vmpc ps -q web)
sudo docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' "$vmp_web_id"
~~~

假设你实际查到 172.20.0.4，在 .env 填：

~~~dotenv
TRUSTED_PROXY_CIDRS=172.20.0.4/32
~~~

不能照抄该地址，不能填用户网段、整个内网、0.0.0.0/0 或 ::/0。保存后只重建后端：

~~~bash
vmpc up -d --no-deps --force-recreate control-plane
~~~

web 重建后 IP 可能改变，要重新检查。需要固定 IP 时使用经过规划、不冲突的专用 Docker 网络；不要盲改现有网络。增加 HTTPS 前置网关后还需要第 18 节的逐层信任，单填这里不够。

## 8. KVM 宿主机检查与依赖

**执行位置：每台 KVM 宿主机，不是控制节点。已有虚拟机的宿主先做只读检查。**

### 8.1 只读检查

~~~bash
hostname
uname -m
test -e /dev/kvm && echo '发现 /dev/kvm'
sudo virsh --connect qemu:///system --readonly uri
sudo virsh --connect qemu:///system --readonly list --all
ip -br link show type bridge
ip address show br0
free -m
df -h /data
command -v virsh qemu-img genisoimage cloud-localds ping arping
~~~

/data 或 br0 不存在时替换为自己的实际路径 / 网桥。这里不会创建网桥、开关机或删除虚机。

需要确认：

- 连接的是 qemu:///system，而不是空的用户 session；
- 原有虚拟机数量和状态符合预期；
- br0 已存在、已启用，并接入正确物理网络；
- 可留给平台的内存、磁盘有明确预算。

**不要为了得到 br0 而远程直接覆盖 Netplan 或切换网卡。** 这可能断开宿主和所有已有虚机；网络改动应单独由网络管理员安排。

### 8.2 arping 和 cloud-localds 是干什么的

| 工具 | 作用 | 是否必须两者都装 |
| --- | --- | --- |
| ping | ICMP 连通性辅助检查 | 当前 Agent 预检需要 |
| iputils-arping | 在指定网桥用 ARP DAD 探测 IP 占用，补足禁 ICMP 设备漏检 | 创建前占用检查需要 |
| genisoimage | 把 cloud-init 配置生成 seed ISO | 与 cloud-localds 二选一 |
| cloud-localds，来自 cloud-image-utils | 生成 cloud-init NoCloud 配置盘 | 与 genisoimage 二选一，无自动 fallback |
| qemu-img | 读取镜像信息、创建 qcow2 增量系统盘 | 需要 |
| virsh | 连接本机 libvirt，查询 / 操作受平台管理的域 | 需要 |

arping 不是随机 ping 整个网段，更不是修改宿主 IP。ARP 探测只能检查可见的同一二层网络，仍不能替代 DHCP / IPAM 的地址规划。

**必须安装 iputils-arping，而不是另一个命令行参数不兼容的 arping 包。**

### 8.3 已有 KVM 宿主：只补缺失工具

先模拟安装，看看是否会升级已有核心组件：

~~~bash
sudo apt-get update
sudo apt-get -s install iputils-arping libcap2-bin genisoimage
~~~

组织确认后仅安装缺失项：

~~~bash
sudo env NEEDRESTART_MODE=l NEEDRESTART_SUSPEND=1 DEBIAN_FRONTEND=noninteractive \
  apt-get install -y iputils-arping libcap2-bin genisoimage
~~~

若选择 cloud-localds，则安装 cloud-image-utils，并在配置中改为其绝对路径。

该命令避免 needrestart 自动安排相关服务重启，但包管理器仍可能更新依赖。不要运行 apt upgrade 或直接重装 libvirt / QEMU；安装前必须看模拟结果。

### 8.4 全新 KVM 宿主的依赖参考

仅适用于全新的 KVM 宿主、没有重要虚拟机：

~~~bash
sudo apt-get update
sudo apt-get install -y qemu-kvm qemu-utils libvirt-daemon-system libvirt-clients \
  genisoimage iputils-ping iputils-arping libcap2-bin curl ca-certificates
~~~

之后按组织规范配置 libvirt 和网桥，再返回 8.1 检查。Agent 不负责安装 hypervisor、创建 bridge 或配置宿主网络。

### 8.5 新建专用 Agent 账号

推荐新部署使用一个专用本机服务账号 vmpagent。它不是平台里的用户账号：

~~~bash
getent passwd vmpagent
getent group libvirt
getent group kvm
~~~

只有 vmpagent 不存在时才创建：

~~~bash
sudo useradd --system --user-group --home-dir /opt/vmlease/vmlease-agent \
  --shell /usr/sbin/nologin vmpagent
sudo usermod -aG libvirt,kvm vmpagent
id vmpagent
~~~

已有部署沿用原账号，不要把 node3、root 或其他既有 Agent 无条件迁到 vmpagent。加入 libvirt 组意味着有本机虚拟化管理权限，不能给无关普通账号。

确认该账号可以只读连接：

~~~bash
sudo -u vmpagent virsh --connect qemu:///system --readonly list --all
~~~

失败时按发行版 libvirt socket / polkit 规范授权，不要开放 TCP libvirt 来绕过。

### 8.6 arping 权限实测

~~~bash
getcap /usr/bin/arping
~~~

通常应有 cap_net_raw=ep。如果没有，管理员经审核后可给这个发行版工具配置能力：

~~~bash
sudo setcap cap_net_raw+ep /usr/bin/arping
getcap /usr/bin/arping
~~~

只给 arping 工具设置需要的能力，不给整个 Agent 设置额外能力。

使用 Agent 账号探测一个**确定已占用**、同网桥可见的地址，例如网关：

~~~bash
sudo -u vmpagent /usr/bin/arping -D -I br0 -c 2 -w 3 10.0.0.1
echo $?
~~~

iputils-arping 的 DAD 模式，收到占用响应会返回非 0；确认没有响应时返回 0。权限错误也可能是非 0，必须同时看输出，不能仅看退出码。该命令不修改 IP 配置。

## 9. 安装 Agent 和建立隔离目录

**执行位置：每台 KVM 宿主。下面是首次安装，不用于覆盖已运行 Agent。**

### 9.1 下载正式发布包

~~~bash
mkdir -p "$HOME/vmp-agent-download-0.5.3"
cd "$HOME/vmp-agent-download-0.5.3"
uname -m
~~~

按架构选择一个包。x86_64 对应 amd64；aarch64 对应 arm64：

~~~bash
# x86_64 宿主选择这一项。
vmp_arch=amd64

# aarch64 宿主改成 vmp_arch=arm64，不要两项都执行。
curl -fL --retry 3 -o "vmlease-agent-linux-$vmp_arch.tar.gz" \
  "https://github.com/lixiaokun777/vmp-agent/releases/download/v0.5.3/vmlease-agent-linux-$vmp_arch.tar.gz"
curl -fL --retry 3 -o SHA256SUMS \
  https://github.com/lixiaokun777/vmp-agent/releases/download/v0.5.3/SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
~~~

下载页：[Agent 0.5.3 正式发布](https://github.com/lixiaokun777/vmp-agent/releases/tag/v0.5.3)。

应显示你下载的包为 OK。只下载一个架构时使用 --ignore-missing，另一架构未下载不是安装失败。没有任何匹配文件或校验失败时停止，不要解压执行。

### 9.2 首次解压

~~~bash
sudo install -d -m 0755 /opt/vmlease
sudo test ! -e /opt/vmlease/vmlease-agent
~~~

上一条不成功说明目录已存在：先核查，不要继续覆盖。空目录场景再执行：

~~~bash
sudo tar -xzf "vmlease-agent-linux-$vmp_arch.tar.gz" -C /opt/vmlease
sudo chown -R vmpagent:vmpagent /opt/vmlease/vmlease-agent
sudo chmod 0700 /opt/vmlease/vmlease-agent
sudo -u vmpagent cp /opt/vmlease/vmlease-agent/conf/agent.env.example \
  /opt/vmlease/vmlease-agent/conf/agent.env
sudo chmod 0600 /opt/vmlease/vmlease-agent/conf/agent.env
~~~

chown -R 只针对这次新解压的发布目录，不针对 /data、已有 VM 目录或旧版正在使用的目录。

目录含义：

~~~text
/opt/vmlease/vmlease-agent/
├── vmlease-agent            Go 二进制
├── control.sh               启停脚本
├── conf/agent.env            私密配置，0600
├── logs/agent.log            运行日志
├── run/agent.pid             进程号
├── run/state/               私密状态，必须长期保留
│   ├── credentials.json     宿主专属身份
│   └── ...                  任务租约、执行和结果回执
└── docs/                    随安装包提供的专题说明
~~~

不要用 vmlease-agent --version 检查版本：当前二进制没有这个命令，可能进入正常运行流程。用下载包版本、SHA256SUMS 和二进制摘要记录版本。

### 9.3 新建平台专用数据目录

先确认这三个目录未被其他业务使用；以下仅针对新的空目录：

~~~bash
sudo install -d -m 0750 -o vmpagent -g kvm /data/vmp-instances
sudo install -d -m 0755 -o root -g root /data/vmp-images
sudo install -d -m 0750 -o vmpagent -g kvm /data/vmp-cache
~~~

| 目录 | 内容 | 为什么这样分开 |
| --- | --- | --- |
| /data/vmp-instances | 新实例系统盘、seed、manifest | 删除只作用于托管实例，不碰存量目录 |
| /data/vmp-images | 管理员提供的原始镜像 | 防止实例写入覆盖模板 |
| /data/vmp-cache | 校验后的内容寻址 backing | 基础缓存会被多台 VM 引用，不能任意删除 |

缓存根必须属于启动 Agent 的账号，父目录不能允许组 / 其他用户写入。目录不能通过符号链接绕到其他位置。

缓存内容目录会被 Agent 封装为运行组可遍历的 0750，内容文件为 0440。libvirt 动态 DAC 可能把已用缓存文件的 owner 改成 QEMU 账号，这是正常情况；不要在运行中的 backing 文件上手工 chown 回 Agent。

## 10. 准备基础镜像

**执行位置：专用镜像制作 / 下载机器；最后复制到宿主镜像目录。**

### 10.1 不要把安装 ISO 当基础镜像

平台接收可直接启动的 cloud image / qcow2，不是 Ubuntu 安装 ISO。基础镜像至少需要：

- cloud-init，能处理 NoCloud seed；
- SSH 服务；
- 与宿主、QEMU 相符的 CPU 架构；
- 启用 Guest Agent，才能完整使用交付检测及密码重置；
- 希望开箱有 Docker / Git 等工具时，提前把工具装进模板。

**Agent 不会在首启时联网给虚拟机安装 Docker 或 qemu-guest-agent。** 不要把“用了官方 cloud image”直接等同于“所有研发工具已经预装”。

### 10.2 下载 Ubuntu 示例

以下以 amd64 Ubuntu 22.04 为例；arm64 宿主选择对应镜像：

~~~bash
sudo apt-get install -y curl ca-certificates qemu-utils
mkdir -p "$HOME/vmp-image-staging"
cd "$HOME/vmp-image-staging"
curl -fL --retry 3 -O https://cloud-images.ubuntu.com/releases/22.04/release/ubuntu-22.04-server-cloudimg-amd64.img
curl -fL --retry 3 -O https://cloud-images.ubuntu.com/releases/22.04/release/SHA256SUMS
awk '$2 == "*ubuntu-22.04-server-cloudimg-amd64.img" || $2 == "ubuntu-22.04-server-cloudimg-amd64.img" {print}' SHA256SUMS | sha256sum -c -
qemu-img info ubuntu-22.04-server-cloudimg-amd64.img
~~~

来源：[Ubuntu 官方 cloud image 发布目录](https://cloud-images.ubuntu.com/releases/22.04/release/)。

应看到 checksum OK，且 qemu-img 显示实际格式为 qcow2。扩展名 .img 不代表格式不是 qcow2。

镜像目录地址会发布新构建。生产请记录下载时间和摘要，固定组织已验收的模板；更严格的信任校验应使用官方签名 / 组织的镜像验签流程。

### 10.3 预装研发工具

推荐在专用镜像制作机器上完成，不要修改正在被 VM 引用的模板 / 缓存。一个可选的 Ubuntu 制作方式：

~~~bash
# 只在专用镜像制作机安装，不在承载重要虚机的宿主上盲装工具链。
sudo apt-get install -y libguestfs-tools
cp ubuntu-22.04-server-cloudimg-amd64.img vmp-ubuntu-2204-amd64.qcow2
sudo virt-customize -a vmp-ubuntu-2204-amd64.qcow2 \
  --install qemu-guest-agent,openssh-server,docker.io,git,curl \
  --run-command 'systemctl enable docker ssh' \
  --run-command 'cloud-init clean --logs'
qemu-img info vmp-ubuntu-2204-amd64.qcow2
sha256sum vmp-ubuntu-2204-amd64.qcow2
~~~

该方法需要 libguestfs appliance 和包源可用，包版本 / Docker 来源按组织要求选择。模板的 Guest Agent 需能由 virtio channel 启动；镜像首次演练必须核实实际 qemu-guest-agent 服务，不以“包安装成功”代替验收。

如组织已有云模板流水线，优先使用既有流水线；不要下载未知来源“已装好一切”的镜像。

模板应清除制作时的账户凭据、SSH 主机密钥及 cloud-init 残留。不要把镜像制作人员的密码或 SSH 私钥留在模板里。使用平台生成的账号 / 一次性密码验证真实首启。

### 10.4 分发到宿主

将**验收后的新文件**复制到宿主，再登记文件名。例如文件已在宿主当前目录：

~~~bash
sudo install -m 0644 -o root -g root vmp-ubuntu-2204-amd64.qcow2 \
  /data/vmp-images/vmp-ubuntu-2204-amd64.qcow2
sudo -u vmpagent qemu-img info /data/vmp-images/vmp-ubuntu-2204-amd64.qcow2
sha256sum /data/vmp-images/vmp-ubuntu-2204-amd64.qcow2
~~~

目标文件已存在且被使用时不要覆盖：用新文件名、新镜像定义和重新验收流程。多宿主可以只在部分宿主准备某个镜像；调度按实际 READY 矩阵选择，不假定所有宿主都有。

## 11. 填写 Agent 配置

**执行位置：KVM 宿主。**

~~~bash
sudo nano /opt/vmlease/vmlease-agent/conf/agent.env
~~~

下面给一份只读纳管的完整示例。地址、令牌、预算、目录、网桥按自己的信息表修改。配置值中不要保留中文占位说明。

~~~dotenv
# 首次只读；三个写闸门暂时都不开。
AGENT_MODE=kvm-readonly
KVM_WRITE_ENABLED=false
KVM_WRITE_CONFIRMATION=disabled

# 每台唯一；管理IP是控制节点能访问的宿主裸IP。
AGENT_NAME=kvm-node01
AGENT_MANAGEMENT_IP=10.0.0.21

# 平台Web根地址，不能包含 /api/v1，不要加末尾斜杠。
CONTROL_PLANE_URL=http://10.0.0.10:8080
AGENT_BOOTSTRAP_TOKEN='填控制节点同一个随机引导令牌'

# 新宿主留空。成功注册自动保存独立凭据。
AGENT_HOST_ID=
AGENT_RUNTIME_TOKEN=
AGENT_STATE_DIR=/opt/vmlease/vmlease-agent/run/state

# 本机虚拟化和工具。
KVM_LIBVIRT_URI=qemu:///system
KVM_VIRSH_PATH=/usr/bin/virsh
KVM_QEMU_IMG_PATH=/usr/bin/qemu-img
KVM_SEED_TOOL_PATH=/usr/bin/genisoimage
KVM_PING_PATH=/usr/bin/ping
KVM_ARPING_PATH=/usr/bin/arping

# 三个目录对应第9节创建的隔离目录。
KVM_STORAGE_ROOT=/data/vmp-instances
KVM_IMAGE_ROOT=/data/vmp-images
KVM_CACHE_ROOT=/data/vmp-cache

# 前期仅用本地镜像，不允许远程下载。
KVM_IMAGE_ALLOWED_HOSTS=
KVM_IMAGE_PRIVATE_HOSTS=
KVM_IMAGE_MAX_GB=10
KVM_IMAGE_CACHE_MAX_GB=40

# 网桥和QEMU运行组；必须与真实宿主匹配。
KVM_ALLOWED_BRIDGES=br0
KVM_RUNTIME_GROUP=kvm

# 固定给平台的总预算；以下只是小规模示例，不是宿主总资源。
ALLOCATABLE_CPU=8
ALLOCATABLE_MEMORY_MB=16384
ALLOCATABLE_DISK_GB=200

# 实时物理余量保护；示例保留10GiB内存和10GiB磁盘。
KVM_SAFETY_MEMORY_MB=10240
KVM_SAFETY_DISK_GB=10

# 先禁用控制台；第17节再成组开启。
CONSOLE_LISTEN_ADDR=
CONSOLE_PUBLIC_URL=
CONSOLE_SIGNING_KEY=
CONSOLE_ALLOWED_ORIGINS=
~~~

保存后：

~~~bash
sudo chmod 0600 /opt/vmlease/vmlease-agent/conf/agent.env
sudo chown vmpagent:vmpagent /opt/vmlease/vmlease-agent/conf/agent.env
~~~

### 11.1 几个常见填错点

- CONTROL_PLANE_URL：填用户能访问且宿主也能访问的平台根地址，不填后端 Docker 内部地址，不填 /api/v1；
- AGENT_MANAGEMENT_IP：填宿主 IP，不是控制节点 IP，不能写 http://、:19090、/24、域名或 IPv6 zone；
- AGENT_NAME：宿主身份名称要唯一、稳定，升级不改名；
- KVM_ALLOWED_BRIDGES：填宿主真实 bridge，多个用英文逗号；
- KVM_SEED_TOOL_PATH：本例 genisoimage。用 cloud-localds 时改为 /usr/bin/cloud-localds，并确认包已装，无自动替代；
- AGENT_STATE_DIR：显式固定，不能每次换目录、删掉或复制别台的 state。

agent.env 被 shell 加载，必须是管理员维护的可信文件。不能把用户提交内容当脚本写进配置。

### 11.2 资源预算到底怎样填

ALLOCATABLE_* 是**给平台的总预算**，不是每次看到的实时剩余量。例如你愿意拿出 40 GiB 内存：

~~~dotenv
ALLOCATABLE_MEMORY_MB=40960
~~~

这里 40960 = 40 × 1024。想拿出 50 GiB 就是 51200。预算仍受宿主物理总量和安全余量约束，不应无条件照抄。

| 配置 | 单位 | 推荐 |
| --- | --- | --- |
| ALLOCATABLE_CPU | vCPU 核数 | 显式填写给平台的总上限 |
| ALLOCATABLE_MEMORY_MB | MiB，字段名沿用 MB | 显式填写总上限，40 GiB 为 40960 |
| ALLOCATABLE_DISK_GB | GiB，字段名沿用 GB | 显式填写平台系统盘逻辑预算 |
| KVM_SAFETY_MEMORY_MB | MiB | 额外给宿主及存量 VM 留的实时内存 |
| KVM_SAFETY_DISK_GB | GiB | 不可被平台耗尽的实时磁盘余量 |

**0 不是“禁止分配”**：CPU 0 使用逻辑 CPU 总数；内存 / 磁盘 0 使用物理总量减安全保留的自动上限。磁盘按专用目录所在文件系统总容量计算，不是一个独立的目录容量配额。

承载旧 VM 的宿主请全部显式填保守正数，不要用 0 猜资源。已有 VM 的实时占用会影响 safe_available，但不会自动替你制定平台预算。

平台配额、已预留和实时安全余量分开计算，见第 13 节。

## 12. 只读纳管

**执行位置：KVM 宿主执行；管理员在浏览器核对。**

### 12.1 先验证平台连通

~~~bash
sudo -u vmpagent curl -fsS http://10.0.0.10:8080/api/v1/health
~~~

使用 HTTPS 时必须正常验证证书；不要用 curl -k 或关闭 Agent TLS 校验作为正式解决方案。

### 12.2 预检

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh preflight
~~~

应输出检查结果，工具、libvirt、目录、网桥和存量域盘点符合预期。只读模式的 CORDONED 是正常状态，不等于失败。

预检不验证引导令牌、注册成功、实际 ARP 能力或控制台所有配置。工具“存在”也不代表账号一定能执行。所以 8.6 的 ARP 实测、平台连通检查和注册后的页面检查不能省略。

### 12.3 启动

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh start
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh status
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh logs 100
~~~

日志命令持续跟随，Ctrl+C 只是退出看日志，不会停止后台 Agent。不要因为看到 start 输出“started”就认定可创建；status 只说明进程存活。

### 12.4 页面必须核对

管理员进入“宿主机”：

- 能看到 kvm-node01，名称正确；
- 模式 kvm-readonly；
- 状态 CORDONED，不参与写调度；
- 最近心跳持续更新；
- libvirt / QEMU / 网桥和资源预算正确；
- 初次纳管时原有虚拟机是 EXTERNAL；
- 既有平台升级时原有合法托管 VM 仍是 MANAGED，不能全部当新外部机。

前端 0.5.2 的宿主卡片增加管理 IP 展示，但没有编辑入口。已发布前端 0.5.1 卡片尚无该字段，可以用下述只读 API 核对。以管理员身份在同一浏览器新标签页打开自己的平台地址加 /api/v1/hosts，例如 http://10.0.0.10:8080/api/v1/hosts。这是只读请求，不需提供密码到 URL。返回 JSON 的 items 数组中找到本台宿主，核对 management_ip 是本台 IP，不能是 Docker 或代理 IP。按实际 facts / 资源字段进一步核对网桥、预算和外部域数量。宿主 API 返回 discovered_instances / external_instances 等计数，不返回逐域清单；域的名称、UUID 和归属要在本台宿主第 12.2 节 preflight 输出的 domains 中核对。当前没有外部域详情页面；不要将只读模式的“进程存活”当作可调度验收。

如果 management_ip 为空，检查 AGENT_MANAGEMENT_IP 后按原账号重启 Agent；不要从 Nginx 的代理来源 IP 猜宿主地址。该 API 需管理员会话，普通用户被拒绝是正常隔离。

### 12.5 保留独立身份并清空引导令牌

注册成功后 credentials.json 会保存在显式状态目录，权限仅 Agent 可读。不要打印其内容。

~~~bash
sudo stat -c '%a %U:%G %n' /opt/vmlease/vmlease-agent/run/state
sudo stat -c '%a %U:%G %n' /opt/vmlease/vmlease-agent/run/state/credentials.json
~~~

确认已成功注册和保存，再把本台 agent.env 的 AGENT_BOOTSTRAP_TOKEN 清空。保留原 state，重启后将用单台独立凭据续注册。

**不要清空控制节点的 AGENT_BOOTSTRAP_TOKEN**：后端启动仍要求合法引导令牌，新宿主还要使用它；轮换也必须是经过计划的操作。

## 13. 开启写模式和设置配额

**执行位置：管理员浏览器和这台宿主。没有完成只读验收不要执行。**

### 13.1 先做准备检查

确认：

1. 第 14 节网络、地址范围、镜像和规格已配置；
2. 原有 VM 清单已记录，专用目录与存量目录隔离；
3. Agent 账号能执行 ARP，网桥真实连到该网络；
4. 镜像和 QEMU 的运行组权限无误；
5. 平台预算不会挤占旧业务；
6. 只会申请专门的测试 VM，不操作原有业务虚机。

### 13.2 打开三重写闸门

编辑 agent.env，仅把这三项改为：

~~~dotenv
AGENT_MODE=kvm
KVM_WRITE_ENABLED=true
KVM_WRITE_CONFIRMATION=enable-kvm-write
~~~

执行：

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh preflight
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh restart
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh logs 100
~~~

继续使用同一账号，不要只在这一步改成 sudo ./control.sh restart，以免 root 读取 / 创建另一套身份或让缓存 ownership 不匹配。

只读纳管可以核验本地模板并报告 READY，但不会封装新缓存或领取写任务。本地缓存在首次 CREATE 时才受控生成；远程镜像必须由写模式 SYNC_IMAGE 下载并校验成功。READY 不等于已经通过 QEMU 权限、首启和 SSH 全流程验收；第一次交付仍需测试。初次等待多个心跳是正常的。

### 13.3 页面设置调度配额

在宿主机页点击“配置调度额度”，同时设置 CPU、内存和磁盘，而不是只改 CPU。管理员 Web 配额不能超过 Agent 上限，也不能降到已预留以下。

例如：

~~~text
Agent总预算：8 vCPU / 16 GiB / 200 GiB
Web调度配额：6 vCPU / 12 GiB / 160 GiB
已预留：2 vCPU / 4 GiB / 60 GiB
预算可分配：4 vCPU / 8 GiB / 100 GiB
~~~

即使预算可分配 8 GiB，当前真实安全可用内存只有 3 GiB，也不能再创建一台 4 GiB 机器。

保留期、停止中的托管实例仍保留完整资源预算和 IP，以保证恢复路径；不要把这些预留当成“重复扣费”直接清掉。

最终恢复 / 允许调度前，确认宿主 ACTIVE、写模式、心跳新鲜、目标镜像和网桥 READY。只读、DEGRADED、陈旧库存或缺镜像 / 网桥时不应参与创建。

## 14. 管理员配置网络、镜像和规格

**执行位置：浏览器，使用管理员账号。**

建议先配置网络、镜像和规格，再完成写模式 READY 检查。

### 14.1 网络 IP

进入“网络 IP”→“新增网络”，填写：

| 页面字段 | 示例 | 实际含义 |
| --- | --- | --- |
| 网络名称 | 研发临时网络 | 用户可理解的名字 |
| 宿主机 Bridge | br0 | 宿主实际网桥，不是虚拟机网卡名 |
| 网段 CIDR | 10.0.0.0/24 | 地址所属网段和前缀 |
| 默认网关 | 10.0.0.1 | 该网段的路由出口 |
| 可分配起始 IP | 10.0.0.130 | 平台地址池起点 |
| 可分配结束 IP | 10.0.0.150 | 平台地址池终点，包含该地址 |
| DNS | 10.0.0.2 | 多个用英文逗号分隔 |
| 允许参与分配 | 勾选 | 用户可以选择此网络 |

网络默认没有预填地址池。平台创建网络不会修改宿主网卡或 bridge，也不会改交换机 VLAN。

保存后：

- 地址池只包含实际配置范围；
- 网关 / 不可分配地址会被排除；
- IP 详情有状态和关联实例；
- 已分配 / 保留期地址不会因为缩小范围被悄悄释放；
- 新范围之外仍存在已分配、预留或隔离的地址时，保存会被拒绝；先查清关联资源并按正常流程处理，再修改范围，不是保存成功后暗中丢弃旧占用。

申请前 Agent 使用 ARP + ICMP 辅助检查占用；有冲突时隔离该地址并尝试下一个候选。地址池耗尽会报告资源问题，不应强行覆盖外部设备。

### 14.2 本地镜像

进入“镜像”→“新增镜像”。本例登记：

| 字段 | 填写 |
| --- | --- |
| 镜像 ID | vmp-ubuntu-2204 |
| 名称 | Ubuntu 22.04 研发模板 |
| 来源 | 本地 |
| 推导出的文件名 | vmp-ubuntu-2204-amd64.qcow2，由本地路径取得 |
| 本地路径 | /data/vmp-images/vmp-ubuntu-2204-amd64.qcow2，或相对文件名 |
| 系统 | ubuntu |
| 版本 | 22.04 |
| SHA-256 | 在运维记录中保留真实摘要；当前本地镜像表单没有单独编辑摘要入口 |
| 希望启用 | 勾选 |

当前表单只在远程来源展示文件名 / SHA-256 输入，本地来源通过路径推导文件名，不要寻找不存在的本地摘要输入框。宿主会探测和校验实际摘要；有统一预设本地摘要要求时需使用管理员镜像 API，不能把手工记录当作已填入平台。

本地路径必须在目标宿主 KVM_IMAGE_ROOT 内，不能有路径穿越或 symlink 逃逸。控制节点不需要存在这个文件。

默认数据库可能有 Ubuntu 22.04 / 24.04 镜像定义，但**定义不代表宿主已准备文件**。不使用的默认镜像停用；实际使用的定义必须对应本机真实模板。

检查目标宿主的镜像代次、摘要和 READY，不只看全局“启用”。修改文件、路径、来源或摘要后，需要新的就绪确认；不要覆盖在用 backing 缓存。

### 14.3 远程 / OSS 镜像，可选

支持 HTTPS 下载地址，不是填任意 URL 立刻可用。需要：

1. 可信来源和预先确认的 SHA-256；
2. Agent 配置精确允许下载域名；
3. 内网 OSS 额外明确允许其私网主机；
4. 写模式宿主执行同步；
5. 下载、校验、格式检查、缓存激活成功；
6. 对应宿主当前代次显示 READY。

例如：

~~~dotenv
KVM_IMAGE_ALLOWED_HOSTS=images.example.com,oss.example.internal
KVM_IMAGE_PRIVATE_HOSTS=oss.example.internal
KVM_IMAGE_MAX_GB=10
KVM_IMAGE_CACHE_MAX_GB=40
~~~

仅给确实需要该镜像的宿主配置。私网白名单必须是下载白名单子集，不支持 localhost / link-local / 任意私网 / 关闭 TLS / 自动跳转重定向。

页面登记远程镜像的 URL、文件名和 SHA-256 后，在该镜像行点“同步到宿主机”，选择目标宿主，再点“提交同步任务”。回到镜像列表，展开该行“各宿主机状态”查看进度、校验时间和错误；更深的原因查看目标宿主 Agent 日志。当前没有独立镜像同步任务详情页，也不要去实例任务历史找 SYNC_IMAGE。没有 READY 就不能用于那个宿主的创建。

当前实现是受限 HTTPS 下载，不是 OSS SDK 账号托管。可使用只读限时签名 URL，但要注意到期和保密，不把完整签名链接放公开文档或群通知。

### 14.4 资源规格

进入“资源规格”，可编辑默认规格或创建：

~~~text
ID：c1m2
名称：轻量型 1C2G
CPU：1 vCPU
内存：2048 MiB
系统盘：40 GiB
启用：是
~~~

当前 Agent 的创建参数边界：CPU 1–64，内存 512–262144 MiB 且为 256 的倍数，系统盘 10–4096 GiB。规格还必须满足实际宿主预算和模板要求，不能只看页面保存成功。

系统盘必须大于等于模板虚拟大小，并纳入宿主磁盘预算。即使 qcow2 初始文件很小，平台仍按申请盘大小预留，不允许据此把 200 GiB 预算无限超配。

已有实例使用创建时的资源快照；修改规格不会自动调整既有虚机。想升级一台虚机的配置属于另一项运维能力，不要把改规格当作在线扩容。

## 15. 第一次申请与功能验证

**执行位置：普通测试账号的浏览器；仅操作专用新建测试 VM。**

### 15.1 先建测试账号

管理员“用户管理”→“创建本地用户”，创建普通用户，例如 deploy-reviewer。登录后普通用户只应看到申请自己的虚机、自己的实例 / 申请及个人相关入口，不能管理宿主、LDAP、其他用户或全平台资源。

### 15.2 申请一台最小规格

填写：

~~~text
实例名：deploy-smoke-01
使用时长：8小时（当前页面提供的最短选项）
规格：轻量型1C2G
镜像：已READY的研发模板
网络：已启用且有可用地址的研发临时网络，目标宿主网桥已就绪
用途：部署验收，仅测试本实例
~~~

当前申请页面提供 8 小时、1 天、3 天、7 天、14 天这五个选项；API 支持的范围不等于页面下拉都有。第一次验收选 8 小时即可，不必等到到期才能测试释放。

7 天以内，即不超过 168 小时，自动创建；超过 168 小时进入管理员审批，审批前不预占宿主或 IP。不要一开始申请 14 天然后等待自动创建。

### 15.3 保存一次性凭据

申请成功后保存一次性密码，使用独立复制按钮并确认“我已保存”。平台不保存可再次展示的密码明文。

审核通过后交付的长租期实例，或者忘记保存初始密码的实例，可在符合交付和运行条件后从详情点击“重置登录密码”，重新生成凭据。这需要镜像的 Guest Agent 正常工作，不是从数据库找回旧密码。

### 15.4 判断交付是否完成

先在实例详情页面检查已分配宿主 / IP、生命周期 / 虚拟化状态、任务结果和错误原因。页面有粗粒度进度，但当前没有完整展示后端的分层交付字段。

进一步验收时，在已登录的同一浏览器打开自己的平台地址加 /api/v1/instances/实例UUID。UUID 可从详情地址 #/instance-detail/ 后取得。返回的 instance 对象中核对：

- delivery_status：READY 表示已完成交付检查；
- delivery_message：未就绪时的具体说明；
- observed_domain_status / last_domain_seen_at：最近真实域观测状态和时间；
- console_available：当前是否符合救援控制台条件。

这是只读请求，管理员可查全平台，普通用户只能查自己的实例。不要把字段放到 URL 查询串，也不要将整份包含内部配置的管理员响应发到群里。

“域已运行”和“系统初始化 / SSH 已就绪”是不同层次。NETWORK_PENDING / GUEST_PENDING 是后端分层交付状态，保留现场用于排查，不因一次 ping 超时直接删盘。最终还要执行下方 SSH 和系统内检查，不能仅凭任务成功断言 Docker / 业务已可用。

从有权限的研发网络执行平台给出的 SSH 命令，例如：

~~~bash
ssh ubuntu@10.0.0.130
~~~

登录后：

~~~bash
cloud-init status --long
systemctl status qemu-guest-agent --no-pager
sudo docker version
~~~

Docker 或 Guest Agent 不存在时修正模板，而不是声称平台自动装了这些工具。

### 15.5 验证功能

仅针对这个测试实例：

1. 关机，等待实际 STOPPED；
2. 开机，确认运行和可登录；
3. 重启，确认操作完成，避免反复点击；
4. 短租期续期，核对新的到期时间；
5. 打开 VNC / 串口，确认可诊断；
6. 重置密码，核对新密码可用；
7. 释放，确认保留期保留原 IP、磁盘和预算；
8. 从保留期恢复，确认原文件和 IP 不变；
9. 立即删除，明确确认不保留 7 天，确认域、平台实例和 IP 按成功结果释放；
10. 检查平台操作审计和任务结果。

恢复最多一次；恢复后再次释放不再获得第二次 7 天保留。执行第 7–9 步前，明确这个测试 VM 没有需要保留的数据。

### 15.6 验证长租期审批

另提专用测试申请，时长 336 小时：

- 普通用户看到待审批，实例不会立即创建；
- 管理员收到待审批入口提示；
- 管理员批准时可以调整为 168 小时；
- 审批单和实际实例到期时间都应按批准的 168 小时，不按原 336 小时；
- 用户可撤回 pending 申请；无人处理 24 小时后超时关闭；
- 续期 / 恢复超过 7 天也走审批，原因不能为空；
- 重复处理已经非 pending 的审批单应提示已处理，不重复创建。

## 16. 多宿主机纳管与调度规则

增加第二台时重复第 8–13 节，不复制第一台整个安装目录和 state。

可以复用：

- 平台根地址；
- 首次纳管引导令牌；
- 控制台签名密钥；
- 经过验收的镜像文件。

必须每台单独配置：

- AGENT_NAME 和 AGENT_MANAGEMENT_IP；
- 实际目录、网桥、运行组和工具；
- 给平台的 CPU / 内存 / 磁盘预算；
- 自动签发的独立 credentials.json。

调度不是简单按宿主列表第一台或固定轮询：

1. 只考虑 ACTIVE、写模式的 KVM 宿主；
2. 排除心跳 / 资源测量 / 镜像就绪陈旧的宿主；
3. 所选镜像当前代次、摘要和所选网络 bridge 在该宿主必须 READY；
4. 检查平台配额减已预留，以及实时安全内存 / 磁盘；
5. 在可选宿主中按调度评分选择并事务预留，防止并发超分配；
6. 由该宿主 Agent 执行任务。

宿主即使还有 CPU，缺内存、磁盘、镜像或网桥，仍不可调度。反过来，某个镜像只在第二台 READY，就只会使用能交付它的宿主。

本版不自动迁移运行中的 VM，不自动把已有外部 VM 接管为平台实例，也不因为 Agent 停止就停止现有虚机。

## 17. 控制台配置

**执行位置：每台需要控制台的宿主；控制节点检查连通；浏览器实际使用。**

### 17.1 填四项，不能只填 URL

Agent agent.env：

~~~dotenv
CONSOLE_LISTEN_ADDR=0.0.0.0:19090
CONSOLE_PUBLIC_URL=ws://10.0.0.21:19090
CONSOLE_SIGNING_KEY='与后端完全相同的随机签名密钥'
CONSOLE_ALLOWED_ORIGINS=http://10.0.0.10:8080
~~~

同时必须有：

~~~dotenv
AGENT_MANAGEMENT_IP=10.0.0.21
~~~

解释：

- LISTEN_ADDR：Agent 在本宿主监听哪里；
- PUBLIC_URL：名字沿用历史，但这里是**控制面连接的内部地址**，不是用户浏览器直接连的 URL；
- SIGNING_KEY：与后端字节完全一致，不能每台重新随机；
- ALLOWED_ORIGINS：用户浏览器实际看到的平台来源，包含协议、主机和非默认端口，不带路径和尾部斜杠。

多个实际合法入口可用英文逗号配置，不能用 *。正式入口改为 https://vmp.example.com 后更新 Origin，旧 http 地址不会自动被认可。

### 17.2 内网 WS 和公网 WSS 的区别

Agent 自身当前监听 HTTP / WS，不原生读取证书。直接写 wss:// 不会自动启用宿主 TLS；内部 WSS 需另外部署受信任的 TLS 代理。

用户使用 HTTPS 时：

~~~text
浏览器 wss://vmp.example.com/api/... → 平台HTTPS网关
控制面 ws://10.0.0.21:19090/... → 内网Agent
~~~

这并不要求每台宿主都有公网证书。内网链路要靠网络隔离和防火墙保护；不可信网络应另外做内部 TLS 或受控隧道。

### 17.3 验证

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh restart
curl -fsS http://127.0.0.1:19090/health
~~~

从控制节点还需要验证宿主该端口可达。路由 / NAT / 防火墙应允许**实际控制面出口来源**，可能是控制节点 IP，不一定是容器 IP。

### 17.4 创建异常时的救援入口边界

当前前端 0.5.2 的 VNC / 串口按钮仅在 RUNNING 详情中显示。后端允许创建中 / ERROR 等场景的受控救援，不等于这些页面已有按钮。

管理员或实例所有者登录后，可在同一个平台域名手工打开控制台页，把实例详情取得的实际 UUID 填入，不填实例名称：

~~~text
https://vmp.example.com/console.html#mode=vnc&instance=实际实例UUID
https://vmp.example.com/console.html#mode=serial&instance=实际实例UUID
~~~

这里不包含票据或宿主地址，控制台页自行向同源授权 API 申请一次性票据。使用 HTTP 内网平台时也要保持同一个实际协议 / Host。仍需要实例未到期、真实域存在且被新鲜扫描确认、合法 metadata 和用户授权；无域、保留期 / 已删除不能用这个链接绕过。

只允许控制节点访问 19090，不对所有平台用户或公网开放。不要为连接成功开放 libvirt TCP 或将 VNC 改成 0.0.0.0。

控制台健康接口可达只证明代理在运行，最终还需登录平台、对专用测试实例验证 VNC / 串口。票据有效 5 分钟，单次核销；刷新旧票据失效应点“重新连接”，不是放宽票据安全校验。

## 18. HTTPS 和可信代理

**执行位置：控制节点 / 组织入口网关。首次内网验证可以先 HTTP；正式使用优先 HTTPS。**

### 18.1 使用已有网关时告诉网络管理员什么

提供：

- 平台域名；
- Web 上游地址；
- 需要完整保留 Host，非默认端口也要保留；
- /api/ 需要 HTTP/1.1、Upgrade 和 Connection；
- WebSocket 合理的长连接超时；
- 访问日志不要记录查询参数，避免控制台票据入日志；
- 每层只信任精确上游，不接受公网客户端伪造的 X-Forwarded-For。

不要只写“代理到 8080”而不提 WebSocket 和客户端 IP，否则控制台 / 审计 / 登录限流会出问题。

### 18.2 控制节点本机 Nginx TLS 示例

同一节点部署入口 Nginx 的情况，可以把 Web 改为仅本机可达：

~~~dotenv
VMP_HTTP_BIND=127.0.0.1
VMP_HTTP_PORT=8080
SESSION_COOKIE_SECURE=true
~~~

保存并重建对应服务：

~~~bash
vmpc up -d --no-deps --force-recreate control-plane web
~~~

web 重建后重新核对第 7.4 节容器 IP 和 TRUSTED_PROXY_CIDRS。

证书由组织签发 / ACME 管理，本例仅展示已经有证书时的转发配置，不含自动申请证书流程。编辑 Nginx 的独立站点文件，不覆盖已有业务站点：

~~~nginx
# 放在http上下文；Ubuntu的sites-enabled通常被http包含。
map $http_upgrade $vmp_tls_connection {
    default upgrade;
    "" close;
}

# 不含query string，防止票据进入日志。
log_format vmp_tls_safe '$remote_addr [$time_local] "$request_method $uri $server_protocol" $status';

server {
    listen 443 ssl;
    server_name vmp.example.com;

    ssl_certificate /etc/nginx/certs/vmp.fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/vmp.key;

    access_log /var/log/nginx/vmp-access.log vmp_tls_safe;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $vmp_tls_connection;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 3600s;
    }
}
~~~

配置保存后 nginx -t，测试成功再按组织流程 reload，不重启已有业务。用户此后统一使用 HTTPS 域名，避免 IP / 域名混用造成 Cookie 和 Origin 不同。

### 18.3 双层代理的客户端 IP：必须另做这一项

前端镜像自带的 Nginx 默认是“直接入口”，用 $remote_addr 覆盖客户端传来的 XFF。在前面再放 TLS 网关时，$remote_addr 就是网关，而不是研发用户。

仅设置后端 TRUSTED_PROXY_CIDRS **不能**恢复已被前端覆盖掉的用户 IP。

正确做法：

1. TLS 网关覆盖不可信的客户端 XFF，写入真实用户地址；
2. 在 web Nginx 只信任这个网关的精确地址，启用 real_ip；
3. web 得到真实 $remote_addr 后继续用现有覆盖规则传给后端；
4. 后端只信任 web 的精确容器 IP。

先从 web 访问日志 / 实际网络拓扑查到网关到 web 的连接来源。Docker 转发时可能是 bridge gateway；不要猜成 127.0.0.1，也不要信任整个内网。

需要自定义时，在控制节点创建一个受控的配置副本：

~~~bash
mkdir -p /opt/vmlease-src/vmp-backend/deployments/local
vmpc cp web:/etc/nginx/conf.d/default.conf \
  /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
sudo chown "$(id -un):$(id -gn)" /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
chmod 0644 /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
nano /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
~~~

在原 server 块内加入，替换成核实过的网关来源：

~~~nginx
set_real_ip_from 172.20.0.1/32;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
~~~

保留原 CSP、安全头、无 query 的日志、/api/ WebSocket、Host 和覆盖 XFF 规则，不复制一个简化站点把它们丢掉。

新建覆盖文件 deployments/local/compose.proxy.yaml，只使用核实过的绝对路径。Compose 多文件中的相对路径按第一个 Compose 文件的目录解析，不是覆盖文件自身的目录；不要误写 ./web-nginx.conf：

~~~yaml
services:
  web:
    volumes:
      - type: bind
        source: /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
        target: /etc/nginx/conf.d/default.conf
        read_only: true
        bind:
          create_host_path: false
~~~

重新定义 vmpc，方案 A 示例：

~~~bash
vmpc() {
  sudo docker compose --env-file /opt/vmlease-src/vmp-backend/.env \
    -f /opt/vmlease-src/vmp-backend/deployments/compose/compose.yaml \
    -f /opt/vmlease-src/vmp-backend/deployments/local/compose.proxy.yaml "$@"
}
~~~

方案 B 只把第一个文件换成 compose.external-db.yaml。以后启动、升级、重建都必须保留这个覆盖文件。

~~~bash
test -f /opt/vmlease-src/vmp-backend/deployments/local/web-nginx.conf
vmpc config --quiet
vmpc run --rm --no-deps web nginx -t
vmpc up -d --no-deps --force-recreate web
~~~

再次核对 web 容器 IP、后端信任地址、响应安全头、登录审计实际用户 IP 和控制台。不要通过持续扩大可信 CIDR 来“修好”日志。

### 18.4 外部数据库私有 CA

若数据库要求私有 CA，把证书作为只读挂载加到同一个自定义 Compose 覆盖中：

~~~yaml
services:
  control-plane:
    volumes:
      - type: bind
        source: /opt/vmp-certs/postgres-ca.pem
        target: /etc/vmp-certs/postgres-ca.pem
        read_only: true
        bind:
          create_host_path: false
~~~

.env 示例：

~~~dotenv
DATABASE_URL='postgres://vmp_app:已编码密码@db.example.internal:5432/vmlease?sslmode=verify-full&sslrootcert=/etc/vmp-certs/postgres-ca.pem'
~~~

控制面镜像运行用户 UID 为 10001，挂载的公开 CA 文件必须能被它读取，例如 CA 文件 0644、父目录可遍历；不要给任何私钥开放相同权限。

证书 CN / SAN 必须匹配连接主机。LDAP / 机器人 / 镜像来源的私有 CA 也要进入**实际发起连接组件**的信任库；仅在你的笔记本信任证书不够。

## 19. 本地用户和 LDAP

**执行位置：管理员浏览器。**

### 19.1 两类账号和两个角色

| 项目 | 行为 |
| --- | --- |
| 平台本地用户 | 管理员创建，密码在平台管理 |
| LDAP 用户 | 同步目录后，用目录密码登录，平台不替 LDAP 改密码 |
| 普通用户 | 申请 / 查看 / 操作自己的实例和申请 |
| 管理员 | 管理全平台资源、用户、配置、审批和审计 |

登录页“平台账号”和“LDAP 账号”分开。同名不同来源不会自动合并；账号和实例归属依用户身份隔离，不按显示名猜归属。

至少保留一位正常启用的本地应急管理员，不能把所有管理员都变成 LDAP，避免目录故障时无法进入平台。

### 19.2 在页面配置 LDAP

进入“LDAP 配置”，填写：

| 字段 | OpenLDAP 示例 | Active Directory 常见对应 |
| --- | --- | --- |
| 地址 | ldaps://ldap.example.internal:636 | ldaps://ad.example.internal:636 |
| Base DN | dc=example,dc=com | dc=example,dc=com |
| 服务账号 DN | cn=vmp-reader,ou=service,dc=example,dc=com | 组织提供的只读绑定 DN |
| 登录过滤器 | (uid=%s) | (sAMAccountName=%s)，按实际目录确认 |
| 同步过滤器 | (objectClass=person) | 使用限定目标用户 / 组的有效过滤器 |
| 用户名属性 | uid | sAMAccountName |
| 显示名属性 | cn | displayName 或 cn |
| 邮箱属性 | mail | mail |

登录过滤器必须包含 %s 用户名占位符。不同目录结构不能直接照抄，尤其不要同步组织的所有账号而不限定范围。

勾选启用，保存配置，测试连接，再手工同步，最后用一个目录测试用户从 LDAP 标签登录。建议使用 LDAPS 或 ldap:// + StartTLS；ldaps:// 不再叠加 StartTLS。

当前没有定时 LDAP 同步，也没有登录时自动创建账号；管理员须先完成手工同步。同名本地用户不会被改为 LDAP，会作为冲突跳过。关闭 LDAP 开关阻止新的目录认证，不主动注销所有已发会话；要立即停用某人，使用用户停用并核对会话权限。

服务账号密码加密保存，页面不回显；留空通常表示不改已有值，清除需要明确勾选清除。环境变量只作引导 / 后备，配置到页面后不要期望改 .env 就覆盖数据库保存值。

同步使用目录分页，但目录大小限制、权限和过滤器仍需实际验证。只有完整同步成功才更新目录存在状态；目录消失的用户会拒绝登录及既有会话，管理员手工停用也不会被同步强制启用。

## 20. 群通知、审批和平台策略

### 20.1 群机器人通知

管理员进入“通知设置”：

1. 填写群机器人 Webhook 的完整 HTTPS 地址；
2. 需要机器人签名时填写它的签名密钥；
3. “平台访问地址”填所有群成员能访问的正式平台根地址；
4. 保存后，在知会群成员的情况下只发一条测试消息；
5. 测试成功再启用自动群通知；
6. 按需开启新审批、失败、宿主异常等事件；
7. 再次点击“保存通知配置”，确认右侧“自动通知”显示已启用。勾选开关不会即时保存，不能勾选后直接离开页面。

WebHook 地址里的 key 是凭据，别放进仓库、截图或公开部署文档。该地址与 Agent 的引导令牌 / 控制台签名不是一个东西。

默认发送 Markdown，到期通常提前 24 小时和 1 小时提醒，还包括保留期 / 最终删除相关提示。系统每分钟扫描，存在排队和重试延迟，不承诺准点秒级发送。

机器人通过用户邮箱 @ 使用人，邮箱要与群账号对应。通知不含虚机密码、控制台票据或原始敏感错误；发送失败不停止租期回收。更多见 [群通知](群通知.md)。

“平台访问地址”用于通知链接，不是一个能自动修改所有组件域名的 PUBLIC_BASE_URL 环境变量。当前应用没有该统一变量。换域名还要修改代理、Agent CONTROL_PLANE_URL / Origin 和相关 Cookie 设置。

### 20.2 审批和代理人

单次创建、续期、恢复不超过 168 小时自动执行；169–720 小时需管理员审批。审批阈值包含“等于 7 天”自动的边界，不是简单按自然日判断。

管理员：

- 从资源总览的待审批提示进入“待我审批”；
- 批准 / 拒绝时记录意见，可调整批准时长；
- 可批量处理同类单据；
- 可按实际入口设置有期限的管理员代理，或转交 pending 单据；
- 交付失败要同时检查审批关联实例 / 任务，已批准不代表交付一定成功。

用户：

- 在“我的申请”查看状态；
- pending 可撤回；
- 被拒 / 超时 / 撤回可按页面提供的短租期重提入口补救；
- 续期 / 恢复提供用途原因。

### 20.3 平台策略

在“平台策略”配置公平使用、自动续期和历史保留。新安装默认：

- 用户资源额度 0 表示不限；
- 自动续期关闭；
- 历史永久保留；
- 单次超过 7 天仍要审批。

生产建议先确定每用户实例数量、CPU、内存、磁盘、未来租期 / 连续使用上限，再通知用户。不要把自动续期等同于永不过期；需要管理员开启、用户主动授权，并受次数和时长上限限制。

审计 / 审批 / 通知历史清理要先归档、下载校验、外部备份和组织授权，再清理精确终态记录。实例立即删除不会顺带删掉操作审计。

## 21. 日常操作与备份

### 21.1 控制节点常用命令

先按自己的 A / B / 覆盖文件定义 vmpc：

~~~bash
vmpc ps
vmpc logs --tail=200 control-plane
vmpc logs --tail=100 web
curl -fsS http://127.0.0.1:8080/api/v1/health
~~~

只重启应用：

~~~bash
vmpc restart control-plane web
~~~

修改 .env 后生效：

~~~bash
vmpc up -d --no-deps --force-recreate control-plane
~~~

停止平台 Web / 控制面不会立即停止正在运行的虚机，但自动租期处理、通知、审批和任务领取会暂停。长时间停平台需要安排人工容量 / 到期管理，不能当作无人值守正常运行。

### 21.2 宿主 Agent 常用命令

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh status
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh logs 200
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh stop
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh start
~~~

使用实际部署账号和目录。stop 只停 Agent，不关机原有虚拟机；脚本最多等待 20 秒，超时拒绝强杀，先调查执行中的任务。

control.sh 使用 nohup，不自动注册开机自启，也没有进程崩溃自动拉起监督功能。重启宿主后按组织运维机制检查并启动 Agent。平台离线通知可辅助发现，但不能代替进程管理。

日志默认 logs/agent.log，需要 logrotate / 日志平台，否则长期运行可能占满盘；轮转示例见 Agent 专题文档。

### 21.3 备份必须包含什么

| 内容 | 备份位置 | 注意事项 |
| --- | --- | --- |
| PostgreSQL | 控制节点或外部数据库系统 | 含用户、配置、审批、任务、IP 和审计 |
| 控制节点 .env / Compose / Nginx | 控制节点 | 含密钥，单独加密并限制访问 |
| 各宿主 agent.env 和完整 state | 每台宿主 | 含独立身份和任务回执 |
| 基础镜像和缓存 | 每台宿主 / 镜像库 | qcow2 backing 依赖必须完整 |
| 每台托管 VM 的磁盘、seed、manifest | 每台宿主 | 数据库备份不会包含这些文件 |
| 发布版本和摘要 | 运维记录 | 便于兼容恢复 |

密钥备份与数据库备份分开保管。复制 state 只是备份，不是创建第二台同身份 Agent。

### 21.4 内置数据库备份

**执行位置：控制节点，方案 A。**

下面用子 shell 的 set -e：任何一步失败都会停止后面的操作，不会把空文件标成成功备份。

~~~bash
(
set -e
sudo install -d -m 0700 -o "$(id -un)" -g "$(id -gn)" /opt/vmp-backups
umask 077
vmp_backup_dir=$(mktemp -d /opt/vmp-backups/vmp-backup.XXXXXX)
cp /opt/vmlease-src/vmp-backend/.env "$vmp_backup_dir/control-plane.env"
cp -R /opt/vmlease-src/vmp-backend/deployments "$vmp_backup_dir/deployments"

vmpc exec -T postgres sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$vmp_backup_dir/database.dump"

test -s "$vmp_backup_dir/database.dump"
vmpc exec -T postgres pg_restore --list \
  < "$vmp_backup_dir/database.dump" > "$vmp_backup_dir/database.list"

sha256sum "$vmp_backup_dir/database.dump"
printf '%s\n' "$vmp_backup_dir"
)
~~~

不 source .env，数据库容器自己读取它已经生效的 POSTGRES_*。如 pg_dump 非 0 或文件为空，备份失败，应停止后续升级。

pg_restore --list 只检查备份结构能读取，不等于已成功恢复。正式上线前还要在独立数据库做恢复演练。

### 21.5 外部数据库备份

使用组织 / 云数据库提供的快照与恢复机制。也可在专用备份机器使用与服务器版本兼容的 pg_dump：

~~~bash
(
set -e
umask 077
mkdir -p "$HOME/vmp-db-backups"
chmod 0700 "$HOME/vmp-db-backups"
vmp_external_backup=$(mktemp -d "$HOME/vmp-db-backups/vmp-backup.XXXXXX")
cd "$vmp_external_backup"
printf '本次备份目录：%s\n' "$vmp_external_backup"
# 使用交互密码输入，避免密码写入命令行或shell历史。
pg_dump --host=db.example.internal --port=5432 --username=vmp_app \
  --dbname=vmlease --password --format=custom --file=vmlease-backup.dump
test -s vmlease-backup.dump
pg_restore --list vmlease-backup.dump > vmlease-backup.list
sha256sum vmlease-backup.dump
)
~~~

每次执行会建立独立私有备份目录，目录内文件名固定但不会覆盖前一次备份。保存输出的目录位置；校验失败时不要继续升级。

TLS、私有 CA、跳板和认证按 DBA 提供的连接方式执行。例如正式库需在当前备份终端设置 PGSSLMODE=verify-full 和 PGSSLROOTCERT=/受控目录/postgres-ca.pem，确保客户端同样验证数据库身份。不要把完整含密码 DATABASE_URL 当命令参数粘贴。

### 21.6 Agent 配置与状态备份

**执行位置：该宿主。示例按 vmpagent 和固定目录。**

~~~bash
(
set -e
sudo install -d -m 0700 /opt/vmp-agent-backups
vmp_agent_backup=$(sudo mktemp -d /opt/vmp-agent-backups/agent-backup.XXXXXX)
sudo cp -a /opt/vmlease/vmlease-agent/conf "$vmp_agent_backup/conf"
sudo cp -a /opt/vmlease/vmlease-agent/run/state "$vmp_agent_backup/state"
sudo cp -a /opt/vmlease/vmlease-agent/vmlease-agent "$vmp_agent_backup/vmlease-agent"
sudo cp -a /opt/vmlease/vmlease-agent/control.sh "$vmp_agent_backup/control.sh"
sudo sha256sum /opt/vmlease/vmlease-agent/vmlease-agent
printf '%s\n' "$vmp_agent_backup"
)
~~~

升级一致性备份应在停 Agent、确认任务无在途后再做；日常热复制 state 不应被当成精确可重放的执行快照。

### 21.7 虚拟机磁盘备份不能直接热拷贝

运行中的 root.qcow2 普通 cp / tar 不保证 guest 文件系统和应用数据一致。生产使用经过演练的 VM 备份 / 快照流程，或按组织要求协调停机后复制所有 backing 依赖。

不要把“写着备份成功”当作数据库、磁盘、身份之间已经一致。灾难恢复需要对账，不允许凭旧账本盲目再创建 / 删除。

## 22. 升级

**已经使用平台的环境从这里开始。不要重新执行 clone、初始化数据库、新建账号或首次纳管。**

### 22.1 先区分旧环境

| 来源 | 关键点 |
| --- | --- |
| 后端 0.5.1 及之后的有效独立身份环境 | 保留现有 host ID、state、账号和密钥，升级修补版本 |
| 0.4.x 共享运行令牌环境 | 身份、资源预算 / 就绪、任务协议一起升级，不能单换后端 |
| 手工运行二进制 / 静态文件挂载 | 使用自己的生效路径，不能套用另一份 Compose |
| 有外部数据库 / 自定义代理 | 所有升级命令保留原 external-db 和覆盖文件 |

本次推荐组合后端 0.5.3、前端 0.5.2、Agent 0.5.3。升级不要求三者版本号相同。

### 22.1.1 本轮的简化升级分支

仅适用于已经正常运行后端 0.5.2、前端 0.5.1、Agent 0.5.3，各宿主均有有效独立凭据的环境：

1. 暂停新业务操作，确认没有在途任务，备份原数据库和配置；
2. 在原部署配置仅修改后端镜像为 0.5.3、前端镜像为 0.5.2；
3. 使用原 Compose 项目、文件及覆盖参数，只拉取和重新创建 control-plane / web，不重建 PostgreSQL；
4. 后端健康后刷新浏览器，检查宿主卡片、用户 / 审计搜索和平台策略；最后恢复入口；
5. Agent 二进制、原账号、名称、配置和状态保持不变。已有正常身份不需要点击“签发 / 轮换凭据”，不重新生成密钥。

本轮没有新的数据库迁移，最高仍为 020；后端启动仍检查既有迁移台账。纯镜像部署无需新环境变量。静态目录挂载部署要整体更新 HTML / JS / CSS，包括新增 management.css，不能让旧挂载覆盖新镜像。

由 0.4.x 共享身份环境升级、Agent 仍旧版、凭据丢失或主动轮换的环境，不适用这一简化分支，必须执行后续完整维护、逐宿主迁移和只读验收流程。

### 22.2 升级前记录

- 实际 Compose 路径、项目名、DB 类型和 Docker 数据卷；
- 原镜像版本 / 摘要和 Git 标签；
- 最高数据库迁移；
- 原 .env 的所有密钥，不重新随机；
- 每台 Agent 的部署账号、目录、state、host ID 和二进制摘要；
- 所有原有域的 UUID、名称和电源状态；
- 原平台通知开关和宿主调度状态。

记录域只用查询，不做开关机：

~~~bash
sudo virsh --connect qemu:///system --readonly list --all
sudo virsh --connect qemu:///system --readonly list --all --uuid
~~~

如果当前仍有用户申请 / 删除 / 审批，单纯暂停调度不等于停止所有写操作。

### 22.3 受控维护窗口

1. 告知用户短暂维护；
2. 在入口阻止新登录 / 业务写操作，但保留 Agent 和健康检查的受控链路；
3. 暂停各宿主调度；不要假定暂停会阻止所有旧任务；
4. 等待正在执行的创建、关机、删除、同步任务结束；
5. 若任务卡住 / 执行结果不确定，先诊断，不强行清掉任务状态；
6. 停止旧 Agent，禁止同一宿主同时运行两个版本；
7. 停止控制面 / Web，做静止数据库和配置备份；
8. 更新配套组件，先恢复 Agent 通道、维持用户维护；
9. 核对心跳、身份、资源和就绪后恢复调度 / 用户入口；
10. 恢复原通知设置，核对未重复发送旧事件。

为了让 Agent 先注册检查，入口网关可在维护期放行 /api/v1/agents/ 和 /api/v1/health，其他用户业务返回 503。让维护规则只对受控 Agent 来源开放，并按现有网关实现。

若需要第 22.6.1 节管理员凭据轮换，还要为明确的管理员运维来源单独放行必要的登录 / auth/me、GET /api/v1/hosts 和目标宿主 POST /credentials/rotate；需要首登改密时仅额外放行对应改密接口。精确限制来源和接口，不向所有用户开放业务写入，也不能绕过原管理员权限、会话或写请求校验。单纯只放行 Agent / health 会挡住这一步管理员操作。完成后撤回临时入口规则。不要在用户仍大量写操作时声称已获得“静止备份”。

### 22.4 更新控制面和前端

先保留旧部署文件，再下载对应版本或更新受控配置。原 .env 只修改目标镜像标签，**不重新 cp .env.example 覆盖密钥**：

~~~dotenv
VMP_BACKEND_IMAGE=lixiaokun/vmp-backend:0.5.3
VMP_FRONTEND_IMAGE=lixiaokun/vmp-frontend:0.5.2
~~~

使用原方案和所有原覆盖文件的 vmpc：

~~~bash
vmpc config --quiet
vmpc pull control-plane web
vmpc up -d --no-deps --force-recreate control-plane
vmpc logs --tail=200 control-plane
vmpc up -d --no-deps --force-recreate web
~~~

新后端启动会继续处理到期资源，每约 15 秒可能产生关机 / 删除任务，没有独立“维护期关闭回收”开关。暂停宿主调度也不阻止旧生命周期任务领取。所以先保持 Agent 停止或三项只读，不因后端 healthy 就立即开放写模式。

迁移成功后、恢复 Agent 写执行前，由管理员 / DBA 在对应库做只读检查：

~~~sql
BEGIN TRANSACTION READ ONLY;
SELECT id, task_type, host_id, resource_id, status
FROM tasks WHERE status IN ('PENDING','RUNNING') ORDER BY created_at;

SELECT id, request_no, status, result->>'execution_uncertain' AS execution_uncertain
FROM approval_requests
WHERE status='PROCESSING'
   OR coalesce(result->>'execution_uncertain','false')='true';

SELECT id, name, lifecycle_status, expires_at, retention_until, restore_count
FROM instances
WHERE (lifecycle_status IN ('RUNNING','STOPPED') AND expires_at<=now())
   OR (lifecycle_status='RETAINED' AND (retention_until<=now() OR restore_count>0));

SELECT id, name, allocation_snapshot_source
FROM instances WHERE allocation_snapshot_source='FLAVOR_FALLBACK';
COMMIT;
~~~

017 迁移会将旧的处理中审批标为 FAILED 并设置 result.execution_uncertain=true，因此不能只查 PROCESSING；查到不确定执行必须先核对真实实例 / 任务，不能直接重复批准。

以上字段是迁移完成后的结构，不能直接套到更早未升级的数据库。查到 pending / 到期不一定代表故障，但必须明确它们恢复 Agent 后将做什么；不确定任务和历史回填快照需核对真实域。不要直接 DELETE 队列或改 expired 时间绕过。

不 pull / recreate postgres；不 down -v；不运行数据库初始化 SQL；不删除迁移台账。若应用迁移失败，保持维护，先查看权限 / 摘要 / 连接错误。

web IP 变化时重新配置精确信任；自定义 proxy 配置与挂载必须保留。

### 22.5 逐台升级 Agent

用第 9 节的方法下载、校验 0.5.3 包，但**先解压到临时 staging 目录，不直接覆盖运行目录**：

~~~bash
vmp_agent_stage=$(mktemp -d /tmp/vmp-agent-stage.XXXXXX)
tar -xzf "vmlease-agent-linux-$vmp_arch.tar.gz" -C "$vmp_agent_stage"
~~~

确认宿主暂停、任务已结束，在原账号下停 Agent：

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh stop
~~~

接着按 21.6 做停机状态的配置 / state / 二进制备份。只替换二进制和控制脚本：

~~~bash
sudo install -m 0700 -o vmpagent -g vmpagent \
  "$vmp_agent_stage/vmlease-agent/vmlease-agent" /opt/vmlease/vmlease-agent/vmlease-agent
sudo install -m 0700 -o vmpagent -g vmpagent \
  "$vmp_agent_stage/vmlease-agent/control.sh" /opt/vmlease/vmlease-agent/control.sh
~~~

已有部署用自己的账号 / 组 / 目录。不要覆盖 conf/agent.env、run/state、PID 之外的执行状态、镜像、实例数据或 backing 缓存。

按新版配置参考增加必要字段，例如原宿主管理 IP 为空时明确填写 AGENT_MANAGEMENT_IP。保留原 KVM_STORAGE_ROOT、IMAGE_ROOT、CACHE_ROOT、运行组、预算和控制台签名。

**明确以只读启动，不只是在页面暂停。** 先编辑原 agent.env，把三项改为：

~~~dotenv
AGENT_MODE=kvm-readonly
KVM_WRITE_ENABLED=false
KVM_WRITE_CONFIRMATION=disabled
~~~

保留其他原值和身份，执行：

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh preflight
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh start
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh status
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh logs 100
~~~

核对原 host ID、外部 / 托管域、预算、目录和第 22.4 节队列。通过后才按第 13.2 节恢复三项写配置，并用原账号 restart，最后管理员恢复调度。已有任务环境不能通过清空 state、改 host name 或创建新身份来“修好”重启。

### 22.6 0.4.x 的独立身份迁移

先阅读 [身份与凭据加固](身份与凭据加固.md)，执行受控备份和停任务流程。

新后端自动迁移至 020。对每个旧宿主：

1. 前端升级到 0.5.2 后，管理员从宿主机页对原宿主单独签发凭据；旧前端没有按钮时才用应急 API，具体见下方 22.6.1；
2. 记录这台 host UUID 和只显示一次的专属令牌；
3. 停止旧 Agent；
4. 仅在本台 agent.env 导入 AGENT_HOST_ID / AGENT_RUNTIME_TOKEN；
5. 启动新版，保存到原固定私有 state；
6. 验证 host ID 不变、独立心跳成功；
7. 清空一次性导入字段，之后用 credentials.json；
8. 全部预算 / 镜像 / 网络就绪确认后才恢复写调度。

旧 bootstrap 不能接管已经存在的宿主名称。身份丢失要管理员重新签发，不能复制其他机器的凭据。

### 22.6.1 旧宿主凭据轮换的实际操作

**仅用于旧共享令牌升级、凭据丢失或明确的轮换计划；已有正常独立凭据的普通升级跳过本节。轮换会使旧值立即失效，请先排空任务并停目标 Agent。**

#### A. 网页签发（前端 0.5.2）

1. 登录已经完成首登改密的管理员账号，进入“宿主机”；
2. 找到原宿主，不删除纳管、不更改名称，点击“签发凭据”；已有独立凭据时按钮为“轮换凭据”；
3. 弹窗核对目标名称、UUID 和管理 IP，确认已停止本台 Agent 且无正在执行的任务，点“确认签发新凭据”；
4. 成功页独立复制 UUID / 一次性令牌，或点“复制 agent.env 片段”取得两行配置。只写入本台原配置，不写到后端或其他宿主；
5. 勾选“我已保存”关闭弹窗。未确认保存时关闭、导航或退出会提醒；浏览器刷新后无法再次查看旧令牌；
6. 目标 Agent 用原账号、名称、状态目录按只读方式导入启动。核对原 UUID、新心跳和资源后再恢复写模式及调度；页面不会自动恢复；
7. 确认 credentials.json 已安全保存后清空两项一次性导入字段，后续读取持久身份，不删除状态目录。

如网络中断 / 返回异常，不能据此断言没有轮换。保持 Agent 停止和宿主暂停，核对后再重新签发；不要连续重复点击。忘记保存的令牌不能找回，重新签发又会使前一个失效。

前端 0.5.2 镜像提供上述按钮；旧前端 0.5.1 镜像不含本轮入口。先更新镜像再刷新页面，不能只刷新旧标签页就认为已有该功能。

#### B. 旧前端的应急 API（不是日常推荐操作）

下述保留给暂未升级前端、自动化集成或排查使用。页面按钮复用相同管理员接口，不降低权限或请求安全校验。

操作位置：已经登录并完成首登改密的管理员浏览器，必须是你自己的平台页面。

先打开浏览器开发者工具 Console，执行只读查看，取得并核对目标宿主 UUID / 名称 / IP：

~~~javascript
(async () => {
  const response = await fetch('/api/v1/hosts', { credentials: 'same-origin' });
  if (!response.ok) throw new Error('读取宿主失败，请确认管理员登录');
  const hostList = await response.json();
  const hosts = hostList.items;
  if (!Array.isArray(hosts)) throw new Error('宿主列表响应格式无效');
  console.table(hosts.map(host => ({
    id: host.id, name: host.name, management_ip: host.management_ip, status: host.status
  })));
})();
~~~

以下代码先要求填 UUID、验证当前管理员身份和宿主名称、二次确认后才轮换，不含预置真实密码。只对已核实的那台执行一次：

~~~javascript
(async () => {
  const meResponse = await fetch('/api/v1/auth/me', { credentials: 'same-origin' });
  if (!meResponse.ok) throw new Error('请先登录');
  const me = await meResponse.json();
  if (me.user.role !== 'ADMIN' || me.user.must_change_password) {
    throw new Error('需要已完成改密的管理员');
  }
  const hostID = window.prompt('填入核实过的目标宿主UUID；取消则不操作');
  if (!hostID || !/^[0-9a-f-]{36}$/i.test(hostID)) return;
  const hostResponse = await fetch('/api/v1/hosts', { credentials: 'same-origin' });
  if (!hostResponse.ok) throw new Error('无法读取宿主');
  const hostList = await hostResponse.json();
  const hosts = hostList.items;
  if (!Array.isArray(hosts)) throw new Error('宿主列表响应格式无效');
  const host = hosts.find(item => item.id === hostID);
  if (!host) throw new Error('UUID不属于当前宿主列表');
  if (!window.confirm('轮换 ' + host.name + ' (' + hostID + ') 的凭据；旧值立即失效，确认已停Agent？')) return;
  const response = await fetch('/api/v1/hosts/' + encodeURIComponent(hostID) + '/credentials/rotate', {
    method: 'POST',
    credentials: 'same-origin',
    headers: { 'Content-Type': 'application/json', 'X-VMP-Request': '1' },
    body: '{}'
  });
  const result = await response.json();
  if (!response.ok) throw new Error(result.error || '轮换失败');
  window.prompt('复制到本台Agent的AGENT_HOST_ID，不发群聊', result.host_id);
  window.prompt('新令牌仅本次返回，复制到本台AGENT_RUNTIME_TOKEN并保护配置', result.runtime_token);
  result.runtime_token = '';
})();
~~~

不要粘贴未知来源脚本，先阅读上述操作含义。新凭据从响应返回一次，在开发者工具 Network 也可能暂存响应，不截图 / 导出 HAR，使用完关闭工具并清理受控剪贴板。

在**目标宿主**配置中导入 host ID 和专属令牌，两项都填，0600，保持只读：

~~~dotenv
AGENT_HOST_ID=本次返回的目标host_id
AGENT_RUNTIME_TOKEN='本次返回的专属runtime_token'
~~~

启动后确认续注册成功和原身份不变，新凭据已原子保存，再清空这两个一次性导入字段。令牌不保存 / 输错时保持暂停，由管理员再次核实并重新签发，不用 bootstrap 接管或改名字重新建宿主。

普通首次新增宿主不用这一套 API：按第 12 节自动取得独立身份即可。

### 22.7 升级成功的判定

- 数据库结构 / 用户 / 配置未丢失；
- 后端、前端健康且版本 / 摘要是目标版本；
- 每台原宿主 ID 不变，独立凭据有效；
- 原域 UUID / 名称 / 状态保持，不误触外部 VM；
- 镜像代次 / 摘要 / 网桥 READY，预算与安全余量合理；
- 权限隔离、审批、保留 IP、控制台、通知正常；
- 用专用测试实例演练，不用原有研发 VM 验证删除。

## 23. 故障恢复与回滚

### 23.1 不同故障不能用同一套“重装”

| 问题 | 优先动作 |
| --- | --- |
| Web 起不来 | 查 Nginx / 网络 / upstream；不动数据库 |
| 后端配置写错 | 恢复已备份配置并只重建后端 |
| Agent 起不来 | 宿主保持暂停，恢复二进制 / 配置，保留 state 和域 |
| 数据库迁移失败 | 保持维护，查连接、权限、摘要；不删台账 |
| 镜像缓存权限失败 | 核对唯一相关目录 / 运行组；不 chmod -R 777 |
| 真实 VM 变更后需要恢复旧数据库 | 先做完整人工对账，不直接旧库覆盖上线 |

后端迁移默认只前进，没有自动 down migration。特别是从 0.4 到 0.5 跨身份 / 任务协议，不能只回滚某一个二进制。

### 23.2 Agent 回滚

仅在确认旧版本兼容当前 metadata / state / 协议且没有不确定在途任务后：

1. 保持宿主暂停；
2. 用原账号 stop；
3. 恢复备份的二进制和匹配配置；
4. 原 state 不随意覆盖，先判断新版本是否已写入任务结果；
5. 明确将三项改为 kvm-readonly / false / disabled，再预检、启动，核对原宿主 ID、域清单、最新任务状态；
6. 通过后才恢复调度。

不要因为二进制回滚就删除新 VM 或缓存文件，也不要同时运行旧 / 新 Agent。

### 23.3 数据库恢复先演练，推荐恢复到独立空库

恢复会改变平台账本，可能覆盖最近的用户、审批和 IP 状态。本手册**不提供对生产库一键 dropdb 的命令**。

推荐流程：

1. 维护入口，停控制面和 Agent，确认无执行中的任务；
2. 确认备份时间、应用版本、密钥和真实宿主状态；
3. DBA 新建独立恢复库，例如 vmlease_restore；
4. 从备份恢复到该空库；
5. 使用隔离应用 / 网络检查数据，禁止新建测试应用自动访问生产 Agent；
6. 核对窗口内真实 VM 创建 / 删除 / 续期和 IP，制定对账方案；
7. 经批准后切换 DATABASE_URL，再恢复配套应用和 Agent；
8. 人工确认无重复创建 / 错误删除后放开用户。

内置 PG 的隔离库演练命令，确认不存在同名库后由管理员执行：

~~~bash
# 仅创建新的演练库，不删除或覆盖原vmlease。
vmpc exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" -O "$POSTGRES_USER" vmlease_restore'
vmpc exec -T postgres sh -c 'exec pg_restore -U "$POSTGRES_USER" -d vmlease_restore --exit-on-error' \
  < /明确的备份目录/database.dump
~~~

不要在生产库上使用 --clean、dropdb 或删除 Docker 卷来“初始化恢复”。恢复后原密钥仍须一致，新的随机密钥无法解密旧配置。

## 25. 常见问题

### 25.1 找不到 vmpc 命令

它是当前终端的函数，不是项目二进制。重新执行 5.2 中对应 A / B 的定义；有 HTTPS 覆盖的，使用 18.3 的多文件定义。或者改用完整 docker compose 参数。

### 25.2 页面打不开 / 502

在控制节点：

~~~bash
vmpc ps
vmpc logs --tail=150 control-plane web
curl -fsS http://127.0.0.1:8080/api/v1/health
~~~

本机正常、外部打不开：查监听地址、端口、路由、DNS 和网关 / 防火墙。502：先查后端 health、自动迁移和容器 DNS control-plane，不要先重装 PG。

### 25.3 后端一直 Restarting

看第一条根因日志：

- 引导令牌无效：不是随机值 / 太短 / 未填；
- password authentication failed：URL 编码、已有密码或凭据不一致；
- database does not exist：外部数据库未由 DBA 创建；
- permission denied：迁移权限 / pgcrypto / schema ownership；
- 迁移摘要不一致：旧 SQL 被改过，不能删除台账绕过；
- bootstrap administrator failed：用户名格式、密码策略或本地应急管理员约束。

### 25.4 数据库密码有 @，填了还是不对

外置 DATABASE_URL 的 @ 编为 %40，! 可编为 %21；数据库密码本身不改。整个 URL 用单引号保护。内置方案不要把编码后的密码拿去做 POSTGRES_PASSWORD 初始化。

### 25.5 登录成功又马上回登录页

HTTP 环境不要把 SESSION_COOKIE_SECURE 设为 true。HTTPS 正式环境应为 true，始终使用同一正式域名和协议。检查浏览器 Cookie 和代理 Host；不要多次错密码导致冷却。

### 25.6 登录提示稍后重试

账号 15 分钟窗口限制 5 次尝试，第 6 次返回 429；来源 IP 每分钟 30 次。不要对真实 admin 连续试错。

很多用户同时被限流：查 7.4 和 18.3 的精确代理信任，可能所有用户共用网关 IP。不要通过删除生产计数或关闭保护解决。

### 25.7 Agent start 成功，平台看不到宿主

status 只证明进程存活。看：

~~~bash
sudo -u vmpagent /opt/vmlease/vmlease-agent/control.sh logs 150
sudo -u vmpagent curl -fsS http://10.0.0.10:8080/api/v1/health
~~~

检查 CONTROL_PLANE_URL、证书、首次引导令牌和本机时间。已有宿主名称不能再用 bootstrap 接管；状态目录丢失时由管理员给该宿主重新签发，不能随便改名生成第二条记录。

### 25.8 宿主一直 CORDONED / DEGRADED

只读模式 CORDONED 正常。DEGRADED 查预检和完整扫描结果。只看网页“恢复调度”不能越过 Agent 三重写闸门。

确认：写模式、工具、账号权限、网桥 UP、镜像就绪、预算和最近心跳。不要让旧 mock / simulator 参与真实调度。

### 25.9 提示没有可调度宿主

逐项检查，不只看 CPU：

1. 至少一个 ACTIVE / kvm 宿主；
2. 心跳和测量未过期；
3. 所选镜像当前代次 / 摘要 READY；
4. 网络 bridge READY；
5. Web 配额减预留满足三种资源；
6. 当前安全剩余内存 / 磁盘满足；
7. 地址池还有可用地址；
8. Agent 是新预算 / 就绪协议。

保留期实例仍占用预算和 IP，不要直接修改 reserved 计数。

### 25.10 镜像文件在，为什么仍失败

核对实际文件名、受限根、当前 SHA-256、镜像代次、格式、模板虚拟大小和 QEMU 运行组。

若提示 backing permission denied：

- 使用 Agent 0.5.3；
- 检查日志指向的**唯一相关缓存目录**；
- 摘要目录应为 Agent 所有、运行组、0750；
- 内容文件 0440 / 正确运行组；owner 可能被 libvirt 动态 DAC 改成 QEMU；
- 不 chown 运行中的 backing 文件；
- 不 chmod -R 777，不停用 AppArmor / SELinux。

管理员核实历史 0700 摘要目录确实属于 Agent、没有越界或危险权限后，可只修正那一个目录到 0750，再由原申请人重试原失败实例；不要递归改整个缓存或存量 VM 目录。

### 25.11 IP 已分配，SSH 连不上

检查：

- 网桥是否在正确 VLAN / 二层网；
- CIDR、网关和 DNS 是否真实；
- IP 与 DHCP / 外部设备是否冲突；
- cloud-init、SSH、Guest Agent 是否正常；
- 用户到 VM 的路由 / ACL 是否允许；
- 详情 API 的 delivery_status / delivery_message，以及页面任务错误中的根因。

不要以 ping 超时就删盘。真实域存在且符合授权时，按第 17.4 节打开同源救援控制台；异常状态页面目前可能没有按钮。地址池耗尽后扩充专用范围再“重试”，后端会重新补齐合法 IP 预留；不是新建一条重复实例。

### 25.12 VNC / 串口连接失败

查管理 IP、19090 内部连通、相同签名密钥、精确 Origin、入口和 web 的 WebSocket Upgrade / Host。

健康接口正常不代表具体实例授权正常；已释放 / 无真实域 / 外部域 / 无所有权会拒绝。旧票据失效点“重新连接”。不要开放所有宿主端口或清除 metadata 来绕过。

### 25.13 LDAP 保存成功，登录失败

依次测试绑定连接、Base DN、过滤器 %s、同步范围、属性映射、目录测试账号密码和平台用户状态。使用 LDAP 标签，不是平台标签。

私有 CA 要进入后端容器信任，不是只装在浏览器。SETTINGS_ENCRYPTION_KEY 改过则旧绑定密码不能解密，恢复原密钥或按受控流程重配。

### 25.14 机器人没收到通知

检查总开关、事件开关、发送记录、Webhook key、签名、服务器时间、证书、控制面出口 IP 和消息平台限制。通知每分钟检查且有重试，不立即发送所有历史事件。

不要拿真实群高频压测。消息平台地址变化要重新保存配置，Agent 无需为改通知升级。

### 25.15 主机重启后 Agent 没起来

control.sh 不提供开机自启。使用原账号 / 原目录启动，检查独立身份、日志和心跳。不要以 root 启动第二份或换一个空 state。按组织运维机制配置开机启动 / 守护策略，保持同账号、同工作目录和固定状态目录。

### 25.16 哪些“清理命令”不能用

不要把以下动作当成排障手段：

- docker compose down -v；
- docker volume rm 生产 PG 卷；
- dropdb 原生产库；
- 删除 schema_migrations；
- rm -rf 实例 / 缓存 / state；
- chmod -R 777；
- 在不知道域归属时 virsh destroy / undefine；
- 把旧 .env 替换成新示例、重新生成已有加密密钥。

必要的删除 / 恢复必须确认精确对象、备份、授权和真实域状态后执行。

### 27.2 自行修改源码时

前后端仓库放在同一父目录，使用受控标签。控制节点已有第 5 节后端目录时，再下载前端：

~~~bash
cd /opt/vmlease-src
git clone --branch v0.5.2 --depth 1 https://github.com/lixiaokun777/vmp-frontend.git
cd /opt/vmlease-src/vmp-backend
~~~

目录已存在时不要重复克隆；按自己的源码分支 / 标签更新。Agent 是单独仓库 / 发布包，不塞进后端容器。

自建镜像不要打成官方的固定发布标签。在 .env 另设：

~~~dotenv
VMP_BACKEND_IMAGE=vmp-backend:local-custom
VMP_FRONTEND_IMAGE=vmp-frontend:local-custom
~~~

方案 A 从后端目录使用构建覆盖：

~~~bash
sudo docker compose --env-file .env \
  -f deployments/compose/compose.yaml \
  -f deployments/compose/compose.build.yaml build --pull
sudo docker compose --env-file .env \
  -f deployments/compose/compose.yaml \
  -f deployments/compose/compose.build.yaml up -d --pull never
~~~

外部数据库把第一个文件替换为 compose.external-db.yaml，不叠加内置数据库方案。存在代理 / CA 覆盖时继续保留相应文件。

Go 工具链、测试数据库和发布门禁参阅各仓库 README；不要在承载重要虚机的宿主上为构建装一整套开发环境。
