# 管理员可选宿主调度策略（0.8.0）

## 开启和使用

先更新本批后端，再更新配套前端。后端启动自动执行 `024_scheduling_policy.sql`，无需手工向 PostgreSQL 挂载 SQL。升级前按部署手册备份数据库；不用修改环境变量、不轮换凭据，也不要求升级 Agent。旧实例不会迁移、重建或重新分配 IP。

管理员登录 → 平台管理 → 平台策略 → 虚拟机调度，选择规则后点击页面底部“保存平台策略”。普通用户不能查看或修改全局策略，也不能调用调度预览接口。新环境、旧环境升级默认均为 `MOST_AVAILABLE`，不会静默切换到均衡或轮询。

| 页面名称 | 协议值 | 选择规则 |
| --- | --- | --- |
| 剩余资源优先 | `MOST_AVAILABLE` | 剩余可分配内存最多者优先；余量相同优先调度序号更小（更久未接单）的宿主 |
| 轮询分配 | `ROUND_ROBIN` | 按纳管时间、UUID 的稳定顺序循环；从上次选中宿主的后一个位置开始，跳过不合格宿主，末尾回到开头 |
| 资源均衡 | `BALANCED` | 计算本次分配后的 CPU、内存、磁盘平台预算占用比例，优先选择三者最大值更低的宿主；同分按最近调度序号轮换 |

均衡计算示例：某宿主分配后 CPU 80%、内存 20%、磁盘 30%，评分为 80%；另一台分别为 40%、50%、20%，评分为 50%，选择后一台。分母是管理员允许平台使用的额度，不是整台物理机容量，也不是 guest 的实时 CPU 利用率。轮询追求接单顺序公平，不保证不同规格申请后的资源占用相同。

所有策略最终平分时按纳管时间、UUID 稳定排序，不再因为宿主名称长期偏向某一台。新宿主按自己的纳管位置加入；暂停宿主恢复后正常轮到它时参与，不补发此前跳过的次数。删除游标指向的宿主也不会重置轮询，因为游标保留原纳管时间和 UUID。

## 所有策略共用的硬条件

- 宿主 ACTIVE，Agent 为 KVM 可写模式，心跳与实时资源采样在 120 秒内且不能超前 30 秒以上。
- CPU / 内存 / 磁盘平台额度减去已预占量能满足本次申请。创建中、失败待清理、关机及保留期实例依现有账本继续占用，不能把关机等同已释放。
- 实时内存、磁盘安全余量足够，并扣除尚未被采样覆盖的创建 / 启动预占，不能在两个计量口径间重复减全部 reserved 或遗漏新预占。
- 选定版本的镜像在宿主已 READY，报告新鲜；网络已启用，目标宿主报告的网桥与网络配置一致且已就绪。

无合格宿主直接返回明确错误，不会降级绕过安全条件。Agent 仍执行原有交付前检查，不因控制面的排序策略放宽 IP 冲突、磁盘或写入保护。

## 并发、失败及生效范围

用户额度检查持有用户事务锁，平台策略持共享锁；调度进度行按事务串行化选择，并锁定目标宿主再次检查。选中记录、平台资源预占、IP 预留、实例、审计和 Agent 任务一起提交或回滚。密码慢散列在全局调度锁之前完成，避免不必要地串行等待。

创建事务使用读已提交隔离级别：等待调度锁后读取前一事务已提交的游标和预占；用户锁、宿主行锁与单事务预占保证配额和容量安全。调度进度存 PostgreSQL，不依赖某一后端进程，重启或多副本不重置轮询。

- IP 池耗尽、写任务失败等提交前错误：全部回滚，不推进轮询。
- 任务已经成功入队但后续 Agent 创建失败：此次分配确实发生，调度序号不倒退；故障按已有任务重试和清理流程处理。
- 超过 7 天的申请提交审批时不调度、不推进游标；批准并实际执行时使用当时已保存的策略。
- 续期、恢复、开关机和已绑定宿主的创建重试：沿用原宿主，不重新选机，避免两边留下同一个实例。
- 保存策略只影响之后的新调度，不进行自动迁移。所有策略共用最近一次成功调度位置；切换到轮询时从最近分配宿主之后开始。

## 只读调度预览

管理员在调度卡片点击“调度预览”，选择策略、规格、镜像和网络，再点“重新预览”。支持试选尚未保存的策略，明确展示预计选中宿主、三项分配后预算占比，以及每台跳过宿主的具体原因。

预览使用与真实调度相同的候选条件及排序函数，使用数据库只读一致性快照。不生成密码、不创建任务、不占资源、不占 IP、不保存配置，也不推进轮询。它不检查某个申请人的用户额度或地址池可用性；预览后状态可能变化，最终以申请或批准时的事务检查为准。宿主变化时实际分配前还会重新锁定并复核。

## 操作追溯与接口

- `GET /api/v1/platform-policy`：包含 `scheduling_strategy`；`PUT` 保存三种枚举之一。旧客户端省略新字段时保留现有策略。
- `GET /api/v1/scheduler`：累计成功调度序号、最近宿主名称、UUID 和时间。这里的成功表示调度事务提交，不等于 guest 交付完成。
- `POST /api/v1/scheduler/preview`：请求 `{strategy, flavor_id, image_id, network_id}`；`strategy` 可省略以使用当前已保存值。须管理员会话及 `X-VMP-Request: 1`。
- 预览返回 `selected_host_id`（无可用宿主时 null）、`reason`、`notice`、`hosts`、`resources`。每台宿主包含 `eligible`、`reasons` 和三个 `projected_*_ratio`（0–1 对应 0–100%，不合格宿主可能超过 1）。
- 实例详情 `instance.scheduling` 和 `application.create` 审计的 `detail.scheduling` 保存当次策略、宿主、选择原因、时间、序号和分配后比例。历史实例返回空快照，不伪造历史调度原因。普通用户仍只能读取自己的实例详情。

本批调度没有 Agent 协议变更，后端和前端固定镜像版本为 0.8.0；删除任务修复另需 Agent 0.7.3。只升级前端会因新接口缺失加载失败，必须先后端后前端。不要把旧标签当作已包含本功能。降级前应先恢复“剩余资源优先”，因为旧控制面不认识新策略字段。

## 验证范围

新增纯排序、真实隔离 PostgreSQL、完整鉴权 HTTP 测试：轮询跨服务对象、游标回滚、只读预览、均衡与内存优先差异、公共排除条件、审批时策略、审计快照、旧客户端兼容、普通用户禁止访问与 CSRF 请求头。12 个不同用户并发申请三台各只能承载两台虚机的宿主，检查只能成功六次且每台预占一致。

使用专用本机 PostgreSQL 执行 `VMP_TEST_DATABASE_URL=... go test -race -count=1 ./...` 和 `go vet ./...`，不要指向生产库。测试创建并清理独立 schema，PostgreSQL 的 `pgcrypto` 扩展需预先装在专用库的 public schema。测试只生成数据库记录与模拟任务，不连接业务 Agent、不创建真实虚拟机，不能宣称生产宿主已验证或已升级。
