# VMP 完整部署指南

当前推荐后端 `0.5.2`、Agent `0.5.3`、前端 `0.5.1`，共同使用 `0.5.1` 的宿主身份、预算与就绪协议。旧环境必须先备份并按第 14 节受控升级。请阅读 [P1 修复与验收](P1修复与验收.md)、[逐台凭据升级](身份与凭据加固.md) 和 [P2 功能与验收](P2功能与验收.md)。不得单换后端接入旧 Agent。

Agent `0.5.3` 修复私有 umask 下缓存目录缺少 QEMU 运行组访问的问题，须同时验证目录 0750、文件 0440 和运行组，不通过 0777、开放组写或停用安全模块绕过。若旧版创建因 backing 文件权限失败，在新 Agent 与精确缓存权限核验后，由原申请人重试该失败实例，保留原 IP/预算关系。

`0.5.2` 仅补修管理 IP 注册：续注册留空保留原地址；Agent 配置 `AGENT_MANAGEMENT_IP` 为控制节点可达的宿主裸 IP，尤其启用控制台时应明确填写。此前被清空的地址需核验后显式补回；不从 HTTP 代理来源地址猜测，无新增迁移。

群机器人租期、审批/交付失败、宿主异常通知的配置和排障见 [群通知](群通知.md)，默认关闭。开启后只通知新事件和宿主异常/恢复边沿，不向群内发送每次心跳。

本文面向第一次接触 VMP 的管理员，目标是在一台控制节点和一台或多台 KVM 宿主机上部署可用的平台。控制节点运行 PostgreSQL、控制面和 Web；每台 KVM 宿主机运行一个 VMP Agent。

## 1. 部署架构

```text
研发用户浏览器
    │ HTTP/HTTPS
    ▼
Web（Nginx，默认 8080）
    │ /api/ 反向代理
    ▼
控制面（Go，容器内 8080） ─── PostgreSQL 16
    ▲
    │ Agent 主动发起 HTTP/HTTPS：注册、心跳、领取任务、回传结果
    │
KVM 宿主机 A / B / C
    └── VMP Agent ─── libvirt / QEMU / qcow2 / cloud-init
```

控制面不会通过 SSH 登录宿主机，也不会直接连接 libvirt。Agent 主动连接控制面；启用控制台时控制面需要访问 Agent 代理端口。浏览器仅通过平台同源 API WebSocket 接入，不需要暴露宿主代理或 libvirt VNC 到公网。

## 2. 当前版本边界

- 控制面和 Web 镜像支持 Linux amd64/arm64；Agent 安装包按实际宿主架构选择。真实 KVM 运行需要宿主架构、QEMU 与镜像架构相符。
- 支持 PostgreSQL 16、Docker Engine 24 及以上版本和 Docker Compose v2。
- KVM Agent 支持 Ubuntu 22.04/24.04 常见的 libvirt/QEMU 环境。
- 新宿主机必须先以 `kvm-readonly` 纳管，确认存量虚拟机、网桥、镜像和存储目录无误后再开启写模式。
- 本地镜像由 Agent 受限打开并纳入安全缓存；远程/OSS 镜像通过 `SYNC_IMAGE` 异步下载、SHA-256 校验、格式检查和原子缓存。只有目标宿主上该镜像及网络就绪，且预算和安全余量均满足，才可调度。私有 OSS 必须明确配置下载允许域名，不能随意关闭 TLS 校验。
- 控制面启动时会自动执行未应用的数据库迁移，并通过数据库锁保护多副本同时启动的场景。

## 3. 资源与网络要求

### 3.1 控制节点

最低建议配置：

| 项目 | 最低值 | 建议值 |
| --- | ---: | ---: |
| CPU | 2 核 | 4 核 |
| 内存 | 4 GiB | 8 GiB |
| 系统盘可用空间 | 20 GiB | 50 GiB 以上 |
| 操作系统 | 支持 Docker 的 64 位 Linux | Ubuntu 22.04/24.04 LTS |

控制节点不存放虚拟机磁盘。PostgreSQL 数据位于 Docker 数据卷，应纳入备份。

### 3.2 KVM 宿主机

- CPU 支持硬件虚拟化，`/dev/kvm` 可用。
- libvirt 和 QEMU 已正常运行，现有虚拟机不需要迁移或停机。
- 有独立的平台虚拟机目录，例如 `/data/kvm-images/ephemeral`。
- 有只读基础镜像目录，例如 `/data/cloud-init/images`。
- 已配置可供虚拟机接入的 Linux bridge，例如 `br0`。
- IP 地址池与网桥处于正确的二层网络，网关、掩码和 DNS 可用。
- 地址池不能与 DHCP 动态分配范围、已有服务器或其他平台重叠。

### 3.3 端口

| 方向 | 默认端口 | 用途 |
| --- | --- | --- |
| 用户 → 控制节点 | TCP 8080，生产建议 443 | Web 和 API |
| Agent → 控制节点 | TCP 8080 或 443 | 注册、心跳和任务 |
| 用户 → 虚拟机 | TCP 22 或业务端口 | SSH 和研发服务 |
| 控制节点 → KVM 宿主机 | TCP 19090，可选 | 平台同源控制台后端代理，建议仅允许控制节点 |

不要开放 libvirt TCP 端口，也不要把 VNC 监听地址改为 `0.0.0.0`。

## 4. 安装 Docker

控制节点需要 Docker Engine 和 Compose 插件。安装后确认：

```bash
docker version
docker compose version
```

当前登录账号需要能够执行 Docker 命令。生产环境请遵循组织的 Docker 安装和权限规范。

## 5. 获取部署文件

使用官方镜像部署时只需要克隆后端仓库，Compose 会从 Docker Hub 拉取固定版本的控制面和前端镜像：

```bash
mkdir -p /opt/vmlease-src
cd /opt/vmlease-src

git clone https://github.com/lixiaokun777/vmp-backend.git
```

需要自行修改前端或从源码构建全部组件时，再克隆同级前端仓库：

```bash
git clone https://github.com/lixiaokun777/vmp-frontend.git
```

部署 Agent 时可以从 GitHub Release 下载压缩包，也可以克隆 `https://github.com/lixiaokun777/vmp-agent.git` 自行构建。

## 6. 生成配置

```bash
cd /opt/vmlease-src/vmp-backend
cp .env.example .env
chmod 600 .env
```

至少修改以下字段：

```dotenv
POSTGRES_DB=vmlease
POSTGRES_USER=vmlease
POSTGRES_PASSWORD=请使用仅包含字母和数字的随机值

AGENT_BOOTSTRAP_TOKEN=请替换为至少32字节随机ASCII值

BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=请设置至少10位且包含大小写字母和数字的密码

SETTINGS_ENCRYPTION_KEY=请替换为至少32位随机值
CONSOLE_SIGNING_KEY=请替换为至少32位随机值

VMP_HTTP_BIND=0.0.0.0
VMP_HTTP_PORT=8080
SESSION_COOKIE_SECURE=false
TRUSTED_PROXY_CIDRS=
```

可以用以下命令分别生成不含 URL 特殊字符的随机值：

```bash
openssl rand -hex 24
openssl rand -hex 32
```

注意：

- `POSTGRES_PASSWORD` 会进入数据库连接 URL，建议只使用字母和数字，避免未编码的 `@`、`:`、`/` 等字符。
- `AGENT_BOOTSTRAP_TOKEN`、`SETTINGS_ENCRYPTION_KEY` 和 `CONSOLE_SIGNING_KEY` 应使用不同随机值。运行令牌改为每台宿主自动取得的独立身份，后端不再配置全局运行令牌；既有环境升级先阅读 [身份与凭据加固](身份与凭据加固.md)，不可单独盲替换后端。
- `SETTINGS_ENCRYPTION_KEY` 丢失后，页面保存的 LDAP 绑定密码无法解密。
- `CONSOLE_SIGNING_KEY` 必须与所有 Agent 完全一致。
- 使用 HTTPS 时将 `SESSION_COOKIE_SECURE` 改为 `true`；纯 HTTP 环境不能设置为 `true`，否则浏览器不会发送登录 Cookie。
- 后端 0.4.4 起默认启用登录保护。经代理访问时需按实际拓扑填写 TRUSTED_PROXY_CIDRS，否则用户共享代理 IP 限制；禁止信任全部网络。配置与验证见 [登录保护](登录保护.md)。

首次管理员创建后仍需要在第一次登录时修改密码。确认管理员可登录后，应清空 `.env` 中的 `BOOTSTRAP_ADMIN_PASSWORD` 并重新创建控制面容器，避免初始密码长期留在容器环境中。

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml \
  up -d --force-recreate control-plane
```

## 7. 启动完整平台

在后端仓库目录执行：

```bash
cd /opt/vmlease-src/vmp-backend

docker compose \
  --env-file .env \
  -f deployments/compose/compose.yaml \
  config

docker compose \
  --env-file .env \
  -f deployments/compose/compose.yaml \
  up -d
```

上述命令默认拉取 `.env` 中指定的 `lixiaokun/vmp-backend:0.5.2` 和 `lixiaokun/vmp-frontend:0.5.1`。生产环境应固定版本号或发布摘要，不要长期使用 `latest`。

控制面容器内已包含全部 SQL 迁移。每次启动都会在健康检查通过前完成以下操作：

1. 连接 `DATABASE_URL` 指向的数据库。
2. 获取 PostgreSQL advisory lock，防止多个控制面副本重复执行。
3. 建立 `schema_migrations` 台账表。
4. 按文件名顺序执行未应用的迁移，每个迁移使用独立事务。
5. 校验已执行迁移的 SHA-256，发现迁移文件被改动时拒绝启动。

数据库用户需要对目标数据库具有创建和修改表、索引及约束的权限，并允许启用 `pgcrypto` 扩展。

### 7.1 使用已有 PostgreSQL

已有 PostgreSQL 时不需要启动项目内置的 `postgres` 容器，也不需要手工挂载或执行 SQL。先在 `.env` 中增加完整连接地址：

```dotenv
DATABASE_URL=postgres://vmlease:密码@postgres.example.com:5432/vmlease?sslmode=require
```

目标数据库可以是空库，也可以是已经由旧版 VMP 初始化过的数据库。然后使用外置数据库 Compose：

```bash
docker compose \
  --env-file .env \
  -f deployments/compose/compose.external-db.yaml \
  config

docker compose \
  --env-file .env \
  -f deployments/compose/compose.external-db.yaml \
  up -d
```

该文件只启动控制面和 Web，不会创建 PostgreSQL 容器或数据卷。如果密码包含 `@`、`:`、`/`、`?` 或 `#` 等 URL 特殊字符，必须先做 URL 编码。

从源码构建时，确保前后端仓库位于同一父目录，然后执行：

```bash
docker compose \
  --env-file .env \
  -f deployments/compose/compose.yaml \
  -f deployments/compose/compose.build.yaml \
  up -d --build
```

网络无法直接拉取 Docker Hub 基础镜像时，可以在 `.env` 中设置 `GO_BUILD_IMAGE`、`RUNTIME_IMAGE` 和 `NGINX_IMAGE` 为组织可信镜像仓库中的等价镜像，再执行源码构建。

查看状态：

```bash
docker compose \
  --env-file .env \
  -f deployments/compose/compose.yaml \
  ps
```

三个服务都应为运行状态，`postgres` 和 `control-plane` 应显示健康。

查看日志：

```bash
docker compose \
  --env-file .env \
  -f deployments/compose/compose.yaml \
  logs -f --tail=200
```

健康检查和页面访问：

```bash
curl http://127.0.0.1:8080/api/v1/health
```

浏览器打开 `http://控制节点地址:8080`，使用初始化管理员登录并按提示修改密码。

日常停止和启动：

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml stop
docker compose --env-file .env -f deployments/compose/compose.yaml start
```

`docker compose down` 会删除容器和网络，但保留具名数据库卷。不要在生产环境执行 `docker compose down -v`，该命令会删除 PostgreSQL 数据卷。

## 8. 首次平台配置顺序

建议严格按以下顺序操作：

1. 在“资源规格”中确认或调整默认规格。
2. 在“网络 IP”中创建网络，填写 CIDR、网关、DNS、宿主机真实网桥名和唯一 IP 起止范围。
3. 在“镜像”中登记本地镜像，`文件名` 必须与每台宿主机 `KVM_IMAGE_ROOT` 下的文件名一致。
4. 在每台 KVM 宿主机安装 Agent，并先以 `kvm-readonly` 启动。
5. 在“宿主机”页面确认物理资源、网桥、libvirt 版本和外部虚拟机盘点结果。
6. 为平台设置保守的 CPU、内存和磁盘调度配额。
7. 完成隔离测试后再开启 Agent 写模式。
8. 使用一个测试账号申请最小规格虚拟机，验证创建、SSH、关机、开机、续期、释放和立即删除。

## 9. 准备基础镜像

推荐使用官方 cloud image，而不是安装 ISO。镜像内必须支持 cloud-init；如果需要页面“重置密码”功能，还必须预装并启用 `qemu-guest-agent`。

以 Ubuntu 为例，在每台可调度宿主机上执行：

```bash
sudo install -d -m 0755 /data/cloud-init/images
sudo cp ubuntu-22.04-server-cloudimg-amd64.qcow2 /data/cloud-init/images/
sudo chmod 0644 /data/cloud-init/images/ubuntu-22.04-server-cloudimg-amd64.qcow2
qemu-img info /data/cloud-init/images/ubuntu-22.04-server-cloudimg-amd64.qcow2
```

多台宿主机必须使用同一文件名和经过校验的相同镜像。可以记录 SHA-256：

```bash
sha256sum /data/cloud-init/images/ubuntu-22.04-server-cloudimg-amd64.qcow2
```

在平台镜像页面登记：

- 来源类型：本地镜像；
- 文件名：`ubuntu-22.04-server-cloudimg-amd64.qcow2`；
- 本地路径：可以填写文件名，或填写 `KVM_IMAGE_ROOT` 内的绝对路径；
- 系统类型：Ubuntu；
- 版本：22.04。

Agent 会拒绝 `KVM_IMAGE_ROOT` 之外的路径、路径穿越和中间符号链接逃逸。已使用的基础缓存是 qcow2 backing 依赖，不能随意手工删除；缓存容量需要单独规划，不能把所有空闲盘都作为 VM 配额。

### 9.1 远程/OSS 镜像

1. 获取可信 cloud image 的 HTTP(S) 地址及官方/内部签名流程确认的 SHA-256，不能用不可信下载本身作为唯一信任来源。
2. 在 Agent 配置中设置允许下载的域名与安全下载容量上限；内网 OSS 需显式允许目标域名。具体变量和重定向规则见 Agent 配置参考。
3. 管理员登记“远程镜像”，填写 URL、文件名、系统及 SHA-256；凭据查询参数不要放进公开文档或群聊，优先使用有限期只读地址。
4. Agent 设置 `KVM_IMAGE_ALLOWED_HOSTS` 精确 HTTPS 主机白名单（默认空，拒绝新下载）；内部 OSS 还须将该主机显式列入 `KVM_IMAGE_PRIVATE_HOSTS`，不能允许 localhost/link-local 或任意私网。`KVM_IMAGE_MAX_GB` 默认 10、`KVM_IMAGE_CACHE_MAX_GB` 默认 40，按磁盘预算调整并保留 `KVM_SAFETY_DISK_GB` 默认 10 GiB 的安全余量。
5. 发起目标宿主同步，在页面观察 PENDING/同步/失败/READY 状态；同一镜像的元数据改变后旧就绪记录失效，需要重新同步。下载拒绝重定向，连接固定已校验的 DNS 地址且仍校验 TLS；本版不托管 OSS SDK 凭据，使用受限 HTTPS 下载地址。
5. 只有目标宿主的镜像和网络都 READY 才会获选；另一宿主缺镜像不会被错误调度。
6. 下载中断或校验失败不激活半成品，保留错误记录并允许管理员修正后重试。

## 10. 部署 KVM Agent

完整 Agent 安装、只读纳管和写模式验收见 `vmp-agent/docs/部署与运维.md`。最短流程如下。

在构建机生成发布包：

```bash
cd vmp-agent
go test ./...
./scripts/build-agent-bundle.sh
```

把 `dist/vmlease-agent-linux-amd64.tar.gz` 复制到宿主机并解压：

```bash
sudo mkdir -p /opt/vmlease
sudo tar -xzf vmlease-agent-linux-amd64.tar.gz -C /opt/vmlease
cd /opt/vmlease/vmlease-agent
sudo cp conf/agent.env.example conf/agent.env
sudo chmod 600 conf/agent.env
```

初次配置必须保持：

```dotenv
AGENT_MODE=kvm-readonly
KVM_WRITE_ENABLED=false
KVM_WRITE_CONFIRMATION=disabled
```

同时填写唯一的 `AGENT_NAME`、控制面地址、首次纳管引导令牌、网桥、专用存储目录和镜像目录。新 Agent 首次取得的独立运行凭据会原子保存，普通重启从本机状态目录读取；旧宿主须管理员单独签发并导入原 host ID，不得使用 bootstrap 接管。然后执行：

```bash
sudo ./control.sh preflight
sudo ./control.sh start
sudo ./control.sh status
sudo ./control.sh logs 200
```

只有在预检全部通过、外部虚拟机识别正确并完成隔离测试后，才可以改为：

```dotenv
AGENT_MODE=kvm
KVM_WRITE_ENABLED=true
KVM_WRITE_CONFIRMATION=enable-kvm-write
```

修改后执行 `./control.sh restart`（使用部署 Agent 的受控账号）。该账号需有 libvirt/KVM、专用目录及网桥探测所需权限；优先使用独立服务账号和最小权限，不要求通过公网以 root 登录。真实 ARP 探测的权限及 `arping` 安装参照 Agent 文档，不可因 ping 不通而跳过占用保护。

## 11. 配置 HTTPS

生产环境建议让现有网关、Nginx、Caddy 或负载均衡器终止 TLS，再转发到 `127.0.0.1:8080`。此时建议：

```dotenv
VMP_HTTP_BIND=127.0.0.1
VMP_HTTP_PORT=8080
SESSION_COOKIE_SECURE=true
```

反向代理至少需要传递 `Host`、`X-Real-IP` 和可信的 `X-Forwarded-For`。不要直接信任公网客户端提供的转发头。

启用控制台时浏览器连接平台同源 `wss://平台域名/api/...`；平台反向代理必须允许 WebSocket Upgrade，控制面到 Agent 地址应仅在受控网络可达。Agent 的 `CONSOLE_PUBLIC_URL` 应是控制面可访问的代理地址，不能将带票据的任意远程 URL交给浏览器。控制台签名、来源校验、所有权和五分钟一次性核销均需保留。

## 12. LDAP

LDAP 可以在管理员“LDAP 配置”页面中维护。建议：

- 使用 `ldaps://`，或在 `ldap://` 下启用 StartTLS；
- 使用只读服务账号；
- 先测试连接，再执行同步；
- 首次同步前确认登录过滤器、同步过滤器和属性映射；
- 同步完整成功后，不再存在的 LDAP 用户标记为目录不可用，拒绝登录及现有会话；管理员设置的启停状态独立保留，不会被目录同步改回启用；
- 备份数据库时同时备份 `SETTINGS_ENCRYPTION_KEY`，但不要把密钥放进数据库备份文件。

## 13. 数据备份与恢复

创建数据库备份：

```bash
cd /opt/vmlease-src/vmp-backend
set -a
. ./.env
set +a

docker compose --env-file .env -f deployments/compose/compose.yaml \
  exec -T postgres pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > "vmlease-$(date +%Y%m%d-%H%M%S).dump"
```

必须额外备份：

- `.env` 中的 `SETTINGS_ENCRYPTION_KEY` 和 `CONSOLE_SIGNING_KEY`；
- 各宿主机的基础镜像；
- 平台专用实例目录。如果只备份数据库，无法恢复虚拟机磁盘数据。

恢复前先停止控制面和 Web，避免恢复过程中产生新写入。恢复操作会覆盖数据库，应在演练后按组织流程执行。

恢复示例：

```bash
cd /opt/vmlease-src/vmp-backend
set -a
. ./.env
set +a

docker compose --env-file .env -f deployments/compose/compose.yaml \
  stop web control-plane

docker compose --env-file .env -f deployments/compose/compose.yaml \
  exec -T postgres dropdb -U "$POSTGRES_USER" --if-exists "$POSTGRES_DB"

docker compose --env-file .env -f deployments/compose/compose.yaml \
  exec -T postgres createdb -U "$POSTGRES_USER" -O "$POSTGRES_USER" "$POSTGRES_DB"

docker compose --env-file .env -f deployments/compose/compose.yaml \
  exec -T postgres pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  --clean --if-exists < vmlease-备份时间.dump

docker compose --env-file .env -f deployments/compose/compose.yaml \
  start control-plane web
```

恢复后检查健康状态、管理员登录、宿主机心跳、实例与 IP 关联。数据库恢复不会自动恢复宿主机上的虚拟机磁盘。

## 14. 升级

1. 阅读三个仓库的 `CHANGELOG.md`。
2. 备份数据库和关键密钥。
3. 拉取前端、后端和 Agent 的目标版本，生产环境建议使用明确的 Git 标签，不要长期跟踪浮动的 `main`。
4. 重新启动控制面；控制面会在对外服务前自动执行未应用迁移。
5. 检查控制面日志中的 `database migrations ready` 和健康检查，确认迁移成功后再开放流量。
6. 逐台升级配套 `0.5.1` Agent，保持原宿主 ID、独立凭据、目录、资源预算和存量域；先观察一台再批量推进。

### 14.1 从 0.4.x 到 0.5.1

1. 先备份数据库、三个组件、Nginx/Compose 配置、Agent `conf` 与 `run/state`；私密文件权限 0600、目录 0700。记录所有存量域 UUID、名称和状态。
2. 暂停新增申请与审批，管理员暂停宿主调度，确认任务无在途；停止旧 Agent，不允许两代 Agent 并行操作同一宿主。
3. 新后端会执行到 `020_platform_governance.sql`。017 迁移分配快照，018 建独立宿主身份，019 分离预算/实时安全余量并建立镜像/网络就绪表，020 建治理策略。历史迁移文件不能修改。
4. 从旧共享令牌升级按 [身份与凭据加固](身份与凭据加固.md) 为每台宿主签发并导入独立凭据。已经运行 018 协议的宿主保留现有凭据，不必重建身份。
5. 新 Agent 首先只读纳管，上报完整清单、预算来源及就绪矩阵。核对外部 VM 不可操作、已有平台实例快照无误，检查 `FLAVOR_FALLBACK` 并人工核对历史分配。
6. 准备本地镜像或受控远程同步，确认匹配的镜像 generation、网桥与网络在目标宿主就绪，再启用写模式和正常调度。未收到新协议或就绪失效时调度应失败关闭，不用关闭安全校验来恢复申请。
7. 升级前端并检查浏览器缓存；验证分页、权限隔离、保留 IP、创建/续期审批以及失败诊断。真实创建验证应使用独立测试实例，不能操作已有研发实例。
8. 新治理配置默认不限制原有资源、不自动续期、不删除历史；管理员在“平台策略”中按组织容量和合规要求启用，审核后通知使用者。

配套版本不可与旧 0.4.x 后端或 Agent 混用。仅替换二进制回滚不安全：017 之后旧 INSERT 不兼容、018 身份改变、019 新调度依赖就绪表。需要审查数据库及宿主操作是否已产生新状态，再制定受控恢复方案。

使用官方镜像更新应用：

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml \
  pull
docker compose --env-file .env -f deployments/compose/compose.yaml \
  up -d
```

源码部署升级时叠加 `compose.build.yaml` 并使用 `up -d --build`。

从 `0.4.0` 或更早版本升级时，数据库里尚无 `schema_migrations` 表。`0.4.1` 的首次启动会以幂等方式检查现有表结构，执行必要的补齐操作并写入 14 条迁移台账。迁移失败时控制面会退出，不会带着半完成的数据库结构对外提供服务。

## 15. 回滚

- 应用回滚：切换前后端到上一个经过验证的 Git 标签，然后重新构建。
- Agent 回滚：保留上一个发布包，停止当前 Agent 后恢复二进制和配置，再执行预检与启动。
- 数据库迁移默认只向前，不自动逆向。发布前必须确认旧应用是否兼容新表结构；不兼容时只能从发布前备份恢复。
- 回滚期间可先将宿主机置为暂停调度，避免产生新任务。

## 16. 常见问题

### 页面显示 502 或无法加载数据

```bash
docker compose --env-file .env -f deployments/compose/compose.yaml ps
docker compose --env-file .env -f deployments/compose/compose.yaml logs --tail=200 control-plane web
```

优先确认 PostgreSQL 和控制面健康，再检查 Web 到 `control-plane:8080` 的容器网络解析。

### 初始化管理员没有创建

确认用户名为 2-64 位字母、数字、点、下划线或连字符；密码至少 10 位并同时包含大写字母、小写字母和数字。查看控制面日志中的 `bootstrap administrator failed`。

### 宿主机一直是 CORDONED 或 DEGRADED

执行 `sudo ./control.sh preflight`，逐项检查工具路径、网桥、libvirt 权限、镜像目录和存储目录。只读模式显示 `CORDONED` 是预期行为；`DEGRADED` 表示至少一项预检失败。

### 提示没有可调度宿主机

确认至少一台 Agent 已进入 `kvm` 模式、宿主机状态为 `ACTIVE`，平台配额大于当前预留，并且规格的 CPU、内存和磁盘均有余量。

### 镜像存在但创建失败

确认平台登记的文件名与目标宿主机文件名完全一致，文件位于 `KVM_IMAGE_ROOT` 内，`qemu-img info` 能读取，并且每台可调度宿主机都已经分发该镜像。

### 虚拟机创建成功但 SSH 不通

检查 IP 是否与 DHCP 或其他设备冲突、网桥是否连接正确物理网络、网关和掩码是否匹配、cloud-init 是否完成以及镜像内 SSH 服务是否启用。0.5.1 Agent 结合 ARP 与 ICMP 检查占用，交付通过 Guest Agent、目标 MAC 与网络可用性分层判断，不能替代正式 IPAM。发现占用时，控制面隔离该地址并尝试下一个 IP；池耗尽后扩容并重试会重新预留地址。禁 ICMP 不再单独触发删盘；已建立托管域但网络未就绪时保留现场，从详情页进入救援控制台排查。

### 登录后立即回到登录页

检查浏览器是否通过 HTTPS 访问。如果当前是 HTTP，`SESSION_COOKIE_SECURE` 必须为 `false`；启用 HTTPS 后应改为 `true`。

### VNC/串口无法连接

确认 Agent 已上报 `console_url`，签名密钥一致，平台精确 Origin 位于 `CONSOLE_ALLOWED_ORIGINS`；防火墙只需允许控制节点访问宿主代理端口。后端固定拨号宿主纳管 IP，代理地址的端口/路径/TLS 名须与该 IP 上的服务匹配。浏览器通过平台同源 ws/wss 接入，检查前置代理是否传递 Upgrade、Connection 和原 Host（含端口），不要放宽 CSP 或公开所有宿主端口来绕过问题。
